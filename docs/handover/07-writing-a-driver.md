# 07 Writing a driver in rustos style

> How to add a driver to rustos, or change one, the way the existing drivers are written. A rustos driver is one Rust module in `firmware/pico2/src/`, built from no outside crates. The board hands it a `DeviceHandle` that exists once per boot. Its constructor takes that handle and puts the hardware block through reset; the constructor or a factory method then programs the registers through raw pointers, and every step cites the RP2350 datasheet by section, table and PDF page. What it returns implements the portable traits of the `api` crate. Logic that never touches a register goes into `api`, where `cargo test` runs it on a computer. This page draws those conventions from the code at master `80bf599`, walks through the PWM driver's real history (rustos #2) step by step, gives a checklist and the commands to run (rustos has no CI), and explains what happens when cw-message-gateway's firmware picks a change up: a new pin, possibly a different firmware image, and a new pass through the safety audit.

This is a process page. It keeps the standard headings, but "How it works" describes the anatomy of a driver and the conventions, "Interfaces and APIs" lists the shared pieces a driver is built from, and "Programming against it" holds the worked example and the checklist. The subsystem pages describe the drivers themselves: [02 Boot and runtime](02-boot-runtime.md), [03 The api crate](03-api-crate.md), [04 Drivers: core](04-drivers-core.md), [05 Drivers: GPIO, USB, PWM, ADC, DMA](05-drivers-io.md) and [06 Multicore](06-multicore.md).

Terms used below, in plain words. The **RP2350** is the microcontroller on the Raspberry Pi **Pico 2** board. A **register** is a 32-bit word at a fixed address that controls a hardware block. A **peripheral** or **block** is one such hardware unit (the PWM, the ADC, the USB controller). **Reset** here means the chip's per-block reset line: most blocks start held in reset and do nothing until software releases them. A **GPIO** is a general-purpose pin; its **pad** is the electrical driver behind the pin, and `FUNCSEL` picks which block drives it. **PWM** is pulse-width modulation, here a square wave on a pin; **ADC** is the analogue-to-digital converter; **DMA** is the block that copies data without the processor. A **UF2** is the firmware file copied onto the Pico 2. A PWM **slice** is one counter with two output **channels**, A and B: the counter counts from 0 to `TOP` at `clk_sys` divided by `DIV`, then **wraps** to 0, and an output is high while the counter (`CTR`) is below that channel's compare value `CC`, so `CC` = 0 means always low. A **DREQ** (data request) is the line a peripheral uses to pace the DMA. On the radio side: **CW** is Morse code; the **keyer box** is a Pico 2 running cw-message-gateway's firmware, which sends Morse by closing a radio's **key line**; **PTT** (push-to-talk) is the line that switches a radio to transmit; an **MCW tone** is an audio tone keyed on and off, which the keyer box plays into a handheld's microphone input from a PWM pin. The **safety audit** is a separate review that clears one exact firmware file, by its SHA-256 hash, before it is flashed or keyed. The rustos handover set has no glossary page; the cw-message-gateway [17 Glossary][gw-17] covers the radio terms.

## How it works

### The anatomy of a driver

![The life of a rustos driver value, using the PWM driver: the board's DeviceHandle, the constructor's three reset steps, the owned driver, the factory that programs a slice and routes a pin, the pin value that implements the api traits, and the off path, with where unsafe code, host tests and build-time checks sit](diagrams/07-driver-anatomy.svg)

*Figure: every rustos driver follows this path; the steps shown are the PWM driver's own. Ownership moves down the left column: each handle is consumed once, so no driver or pin value can be made twice. Notice that the PWM constructor only resets; the slice is programmed in the factory, when its first pin is claimed.*

1. **The board makes the handle once.** [`define_board!`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/api/src/device/mod.rs#L239-L322) generates a board struct with one `DeviceHandle<T>` field per device. `Rp2350::take()` hands it out once per boot: it flips an `AtomicBool` with `compare_exchange`, so every later call, from either core, gets `None` ([`api/src/device/mod.rs:314-319`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/api/src/device/mod.rs#L314-L319)). The Pico 2's device list is in [`firmware/pico2/src/common/board.rs:134-144`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/board.rs#L134-L144).
2. **The constructor consumes it.** `Rp2350Pwm::new(_handle: DeviceHandle<Rp2350Pwm>, _clocks: &Rp2350Clocks) -> Self` ([`pwm.rs:614-625`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L614-L625)) takes the handle by value. `DeviceHandle` is neither `Copy` nor `Clone` ([`api/src/device/mod.rs:130-137`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/api/src/device/mod.rs#L130-L137)), so a second `new(board.pwm)` is a compile error. Hardware bring-up happens here, when the device is claimed, not at `take()` ([`board.rs:20-33`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/board.rs#L20-L33)).
3. **The constructor resets the block,** citing the datasheet at each step. `Rp2350Pwm::new` does exactly three things: release the shared pin blocks and wait for them, set every pin a warm reset left routed to the PWM back to the null function, and cycle the PWM block through reset ([`pwm.rs:614-625`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L614-L625)). It programs no PWM register. A driver whose configuration does not depend on a request programs it here instead: `Rp2350Adc::new` also starts `clk_adc`, writes `CS.EN` and waits for `READY` ([`adc.rs:444-460`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/adc.rs#L444-L460)).
4. **It returns an owned driver value.** It is zero-sized (`_private: ()`) unless it must remember something the hardware cannot report, as `Rp2350Pwm` remembers which outputs it handed out ([`pwm.rs:579-593`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L579-L593)).
5. **Factory methods consume pin handles** (or other tokens) and return owned values, such as `square_from_handle(pin, hz)` returning `Result<Rp2350PwmSquare<N>, PwmError>` ([`pwm.rs:653-693`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L653-L693)). The factory is where the PWM programs hardware: it checks the request, then, for the first pin on a slice, programs and starts the slice with `start_slice` and routes the pin with `connect_pin` ([`pwm.rs:676`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L676), [`pwm.rs:691`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L691)).
6. **Those values implement the `api` traits**: `ErrorType` plus `Write<bool>` for a PWM output ([`pwm.rs:770-804`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L770-L804)). Application code is written against the traits.
7. **`Drop` puts the hardware in its safe state** where dropping should change the hardware: a PWM output turns its tone off ([`pwm.rs:806-811`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L806-L811)), an ADC stream stops the converter and the DMA channel ([`adc.rs:670-689`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/adc.rs#L670-L689)). A GPIO output does not: dropping it leaves the pin driving its last level, which its doc gives as one of the two places the ownership guarantee ends ([`gpio.rs:207-216`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/gpio/gpio.rs#L207-L216)).

`unsafe` code stays inside the driver. Public methods are safe, except where the caller must promise something the compiler cannot check (see [unsafe and its comments](#unsafe-and-its-comments)). Tests run in two places: logic in `api` is unit-tested on a computer, and arithmetic in `pico2` is checked by `const` assertions when the crate builds.

### File layout and the order inside a module

A driver is one file, `firmware/pico2/src/<name>.rs`, declared with `pub mod <name>;` in [`lib.rs:108-117`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/lib.rs#L108-L117). The two drivers that are directories split register layouts from driver logic: `gpio/mod.rs` holds the layouts and `gpio/gpio.rs` the driver; `usb/hw.rs` the layouts and `usb/mod.rs` the driver. A new driver for one block is one file, as clocks, timer, SysTick, watchdog, PWM, DMA and ADC are.

### Claiming the device handle

A new device gets a handle by adding one line to the `devices` block of the board and one `use` line above it ([`board.rs:86-94`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/board.rs#L86-L94), [`board.rs:134-144`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/board.rs#L134-L144)). Update the board's module doc, which lists every device handle and the bring-up order the constructors enforce ([`board.rs:20-33`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/board.rs#L20-L33)).

The constructor's signature carries the rules:

- **The handle by value**, named `_handle` because the body never reads it. Possession is the whole check; there is no runtime state ([`gpio.rs:123-131`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/gpio/gpio.rs#L123-L131)).
- **Proof of order as a borrowed reference.** A driver whose registers or frequencies depend on the clock tree takes `&Rp2350Clocks`, which only `Rp2350Clocks::new` can make ([`clocks.rs:363-387`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/clocks.rs#L363-L387)). USB also takes `&Rp2350Timer`. DMA needs neither and takes none ([`dma.rs:243`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/dma.rs#L243)). The result is that "clocks first" is a type error to forget.
- **`-> Self` when nothing can fail**, because the only failure, a second construction, is already a compile error ([`gpio.rs:123-131`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/gpio/gpio.rs#L123-L131)). **`-> Result<Self, E>`** when the hardware can refuse, as the ADC's `READY` bit can ([`adc.rs:444-460`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/adc.rs#L444-L460)).

Factory methods follow the same rule one level down. They take a `PinHandle<N>` by value (`_handle: PinHandle<N>`) and check `N` at build time by **referencing** an associated constant:

```rust
// pwm.rs:757: the assertion
const PIN_EXISTS: () = assert!(N < MAX_GPIO_PIN);
// pwm.rs:660: the reference that makes the compiler evaluate it for each N
let () = Rp2350PwmSquare::<N>::PIN_EXISTS;
```

An associated constant is only evaluated where it is used, so the reference is what makes it work ([`pwm.rs:753-757`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L753-L757), [`pwm.rs:658-660`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L658-L660)). The ADC does the same for pins 26-29 and for the DMA channel number ([`adc.rs:484-485`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/adc.rs#L484-L485), [`adc.rs:579`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/adc.rs#L579), [`dma.rs:185`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/dma.rs#L185)). The GPIO driver's `_VALID` constants are never referenced, so they check nothing, as its own comment says ([`gpio.rs:233-239`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/gpio/gpio.rs#L233-L239)). Copy the PWM pattern, not the GPIO one.

A driver that hands out parts of a block makes a token per part. `Rp2350Dma::new` returns sixteen zero-sized `Rp2350DmaChannel<C>` fields, and a driver that needs a channel takes one by value ([`dma.rs:170-234`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/dma.rs#L170-L234)). A driver that allows only one user of the whole block consumes itself: `Rp2350Adc::stream_from_handle(self, ..)` ([`adc.rs:477-483`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/adc.rs#L477-L483)).

`DeviceHandle::new` and `PinHandle::new` are `const unsafe fn`s for host tests and for hardware no board describes yet; their `# Safety` sections say the caller then guarantees there is no second handle and, for a `PinHandle<N>`, that pin `N` exists ([`api/src/device/mod.rs:81-95`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/api/src/device/mod.rs#L81-L95), [`api/src/device/mod.rs:139-161`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/api/src/device/mod.rs#L139-L161)).

### Register access

Every access follows the rules in [`gpio/mod.rs:16-43`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/gpio/mod.rs#L16-L43):

1. **Base address from `RegAddr`.** Each block is a variant of `#[repr(usize)] pub enum RegAddr`, named exactly as the datasheet names the block, in address order, with a doc comment that says what the block is, which module uses it and where the base address comes from ([`reg.rs:52-57`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/reg.rs#L52-L57), [`reg.rs:102-105`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/reg.rs#L102-L105)). Two exceptions in the older entries: the reset controller's variant is `RESET`, though the datasheet and its own doc call the block `RESETS`, and four variants (`RESET`, `IO_BANK0`, `PADS_BANK0`, `SIO`) have no "Base from" sentence ([`reg.rs:72-83`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/reg.rs#L72-L83), [`reg.rs:143-154`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/reg.rs#L143-L154)). Every new variant should have one. Arm core registers outside the RP2350 peripheral map are not in `RegAddr`; SysTick's base is a local constant ([`systick.rs:52-54`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/systick.rs#L52-L54)).
2. **A `#[repr(C)]` layout struct** with one `u32` field per register, explicit `_reserved` padding for holes, a doc comment per field (name, table, page, reset value, the bits used), and `const _: () = assert!(core::mem::offset_of!(..) == ..)` for the offsets that matter ([`pwm.rs:218-263`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L218-L263)).
3. **Cast, then project with `&raw`.** `RegAddr::PWM as usize as *mut Pwm` (an enum cannot be cast straight to a pointer, [`reg.rs:8-15`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/reg.rs#L8-L15)), then `&raw mut (*p).field`. **Never form a `&` or `&mut`** to a register: a reference lets the optimiser hoist a load out of a poll loop, which then hangs ([`gpio/mod.rs:18-28`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/gpio/mod.rs#L18-L28)).
4. **Every access is `read_volatile` or `write_volatile`** ([`gpio/mod.rs:29-31`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/gpio/mod.rs#L29-L31)).
5. **Use the atomic aliases instead of read-modify-write** where another core or handler could touch the same register. Most blocks are mirrored at `+0x1000` (XOR), `+0x2000` (set bits) and `+0x3000` (clear bits) ([`reg.rs:29-51`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/reg.rs#L29-L51)). The PWM driver has a helper per view ([`pwm.rs:270-285`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L270-L285)). SIO (single-cycle I/O, the block next to the processors that holds the GPIO output and output-enable registers) has no aliases and offers its own `SET`/`CLR` registers ([`gpio.rs:297-318`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/gpio/gpio.rs#L297-L318)); the USB dual-port RAM has none either ([`reg.rs:133-137`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/reg.rs#L133-L137)).
6. **Never write a register narrower than 32 bits** to change half of it: the RP2350 replicates a narrow write across the bus (§2.1.5, cited at [`pwm.rs:171-178`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L171-L178)). The PWM driver writes one channel's half of `CC` with one 32-bit store through the set or clear alias ([`pwm.rs:788-803`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L788-L803)).

The pattern, from the PWM driver:

```rust
// pwm.rs:271-273: the normal view
const fn pwm() -> *mut Pwm {
    RegAddr::PWM as usize as *mut Pwm
}
// pwm.rs:799, inside an unsafe block: one store through the clear alias
(&raw mut (*pwm_clr()).slice[slice].cc).write_volatile(CC_HALF_MASK << shift);
```

### Reset

[`common/reset.rs`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/reset.rs) wraps the `RESETS` block. Its register polarity is the trap: in `RESET`, **1 holds a block in reset and 0 releases it**, and `RESET_DONE` is the other way round (1 = ready) ([`reset.rs:35-58`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/reset.rs#L35-L58), [`reset.rs:183-188`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/reset.rs#L183-L188)). Each driver names its bits as constants with their citation, such as `const RESET_PWM: u32 = 1 << 16;` under "`PWM` — bit 16 of `RESETS.RESET` (Table 534, p504)" ([`pwm.rs:315-319`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L315-L319)). Which helper a driver calls depends on who owns the block:

| Situation | Call | Example |
|---|---|---|
| The driver owns the block and wants it in a known state, even after a debugger's warm reset (which restarts the processors but not the blocks) | `cycle_reset(MASK)`: assert, release, wait until ready. The mask is **not** complemented. | [`pwm.rs:619`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L619), [`timer.rs:193`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/timer.rs#L193), [`dma.rs:244`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/dma.rs#L244) |
| The block is shared with other drivers (`IO_BANK0` bit 6 and `PADS_BANK0` bit 9 for pins, `SYSCFG` bit 20) | `clr_reset_reg(!MASK)` then `wait_for_reset_done(MASK)`: release only, never assert, because asserting would disturb pins or settings other drivers own. Note the complemented mask. | [`pwm.rs:616-617`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L616-L617), [`adc.rs:447-448`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/adc.rs#L447-L448), [`watchdog.rs:622-627`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/watchdog.rs#L622-L627) |
| Code that can run at any point of a boot, such as a panic path, and must not touch a block still held in reset | `is_reset_done(MASK)`, one read, no wait | [`pwm.rs:722-724`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L722-L724) |

Never put bits 7 (`IO_QSPI`) or 10 (`PADS_QSPI`) in a mask passed to `set_reset_reg` or `cycle_reset`: those blocks carry the flash the program runs from, and resetting them stops the program with no fault and no output ([`reset.rs:157-169`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/reset.rs#L157-L169), [`reset.rs:240-244`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/reset.rs#L240-L244)). `set_reset_reg` alone is not called by any driver at master; `cycle_reset` is the way to assert.

### Routing a pin to a block

A driver that drives a pin from its own block (PWM, ADC) does the GPIO driver's sequence with its own `FUNCSEL` value, using the layouts `IoBank` and `PadsBank` that `gpio/mod.rs` makes `pub(crate)` for this purpose ([`gpio/mod.rs:33-36`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/gpio/mod.rs#L33-L36)):

1. Pad first: for an output, clear `OD` (output disable) and set `IE` (input enable); pulls as the driver needs.
2. `GPIOn_CTRL.FUNCSEL` = the block's function number, written as a whole register so the override fields go back to "normal".
3. Clear the pad's `ISO` (isolation) bit **last**. Until then the pad holds its latched state.

The GPIO driver documents the order ([`gpio.rs:347-361`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/gpio/gpio.rs#L347-L361)), the PWM driver repeats it ([`pwm.rs:886-911`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L886-L911)), and the ADC's analogue input sets the null function, `IE` off, `OD` on and the pulls off, again with `ISO` last ([`adc.rs:747-765`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/adc.rs#L747-L765)). An output must be at its off level before step 3: the PWM driver starts the slice at 0 % and waits for a counter wrap first ([`pwm.rs:109-137`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L109-L137)).

Only the layouts are shared. Each driver declares its own pad and `GPIOn_CTRL` bit constants and its own `RESET_IO_PADS` mask, each with its table and page: `FUNCSEL_PWM` (4, column F4 of Table 644), `FUNCSEL_MASK`, `GPIO_CTRL_NULL`, `PAD_ISO`, `PAD_OD`, `PAD_IE` in the PWM driver ([`pwm.rs:295-319`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L295-L319)); `GPIO_CTRL_NULL`, the pad bits and the pulls in the ADC ([`adc.rs:270-289`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/adc.rs#L270-L289)). A new driver that routes a pin declares its own, including its own `FUNCSEL` number from Table 644.

A warm reset leaves `IO_BANK0` and `PADS_BANK0` as they were, so a pin the previous run gave to a block can still be connected when the new run starts. `Rp2350Pwm::new` therefore sets every pin whose `FUNCSEL` is the PWM back to the null function before it resets the PWM ([`pwm.rs:139-149`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L139-L149), [`pwm.rs:855-873`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L855-L873)). A new driver that drives pins needs the same step.

### Bring-up requirements: what to check and cite

Each driver's module doc has a `# Bring-up requirements` section that answers three questions, each with its citation. Answer all three from the datasheet for a new block, and write the answer down even when it is "nothing to do":

- **Reset.** The block's bit in `RESETS.RESET` (Table 534, p504) and which helper the constructor calls (see [Reset](#reset)), plus any shared block it releases. PWM: bit 16, a full cycle, and `IO_BANK0`/`PADS_BANK0` released only ([`pwm.rs:182-188`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L182-L188)). DMA: bit 2, a full cycle, which also clears every channel's `SECCFG` lock ([`dma.rs:31-37`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/dma.rs#L31-L37)).
- **Clock.** The clock the block runs on, its `CLK_*_HZ` constant (see [Clock constants](#clock-constants-a-driver-uses)), and the gate in `WAKE_EN0`/`SLEEP_EN0` (Table 586, p546) that lets that clock reach the block, saying whether `clocks` touches it. PWM: `clk_sys` through `CLK_SYS_PWM`, `WAKE_EN0` bit 25, enabled out of reset and not touched ([`pwm.rs:26-29`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L26-L29)). DMA: `CLK_SYS_DMA`, bit 7 ([`dma.rs:38-41`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/dma.rs#L38-L41)). ADC: `CLK_SYS_ADC` and `CLK_ADC_ADC`, bits 3 and 2, and `clk_adc` itself, which `start_clk_adc` starts ([`clocks.rs:427-433`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/clocks.rs#L427-L433)). If a frequency the driver computes depends on the clock tree, take `&Rp2350Clocks`.
- **Security.** Who may reach the block's registers. Give the block's `ACCESSCTRL` default, as the PWM does ("Defaults to Secure access from any master", Table 946, p849-850, [`pwm.rs:191-192`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L191-L192)), and any security register of the block's own: every DMA channel resets Secure and Privileged (`SECCFG_CHn` S = 1, P = 1, Table 1183, p1136), "the level this crate's code runs at" ([`dma.rs:42-51`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/dma.rs#L42-L51)).

The security question is the one that has caused trouble. rustos code runs Secure and Privileged, but an application may drop to unprivileged mode: cw-message-gateway's one-Pico image runs its decoder on core 1, unprivileged (cw-message-gateway PR #31, draft, not on main). Core 1 there reads DMA channel 0's registers, which stay Secure Privileged, and the safety audit found that, as first written, the image would bus-fault and reset the box about every 0.5 s (`audit/report.md`, the PR #31 check at `8d5fcf6`, project files). rustos has no API for a channel's security level, so the image now writes `SECCFG_CH0` itself; see [08 Changes made for cw-message-gateway](08-changes-for-cw-gateway.md) and [06 Multicore](06-multicore.md). A block that a new driver expects unprivileged code to reach needs its access set explicitly, and the driver's doc must say how.

### Errors

Every driver value implements `api::common::ErrorType` and names its error type there ([`api/src/common/mod.rs:48-60`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/api/src/common/mod.rs#L48-L60)). The conventions:

- **One error enum per driver**, `PwmError`, `AdcError`, `UsbError`, with `#[derive(Clone, Copy, Debug, PartialEq, Eq)]` ([`pwm.rs:537-577`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L537-L577), [`adc.rs:391-421`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/adc.rs#L391-L421), [`usb/mod.rs:296-304`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/usb/mod.rs#L296-L304)). The trait only requires `Debug`, deliberately not `core::error::Error` ([`api/src/common/mod.rs:40-47`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/api/src/common/mod.rs#L40-L47)).
- **Struct variants that carry the numbers**: `FrequencyOutOfRange { hz, min, max }`, `SliceFrequencyConflict { slice, running_hz, requested_hz }`. Each variant's doc says when it happens and what state the hardware is left in.
- **Check before writing.** The PWM factory finds every error except `NoWrap` before it writes a register ([`pwm.rs:642-652`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L642-L652)); the ADC's only stream error is found "before anything is written" ([`adc.rs:473-476`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/adc.rs#L473-L476)).
- **`core::convert::Infallible`** for operations that cannot fail once the value exists, such as switching a PWM tone or a GPIO pin ([`pwm.rs:768-772`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L768-L772), [`gpio.rs:272-291`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/gpio/gpio.rs#L272-L291)). The trait's doc warns against using it merely because failure is unlikely ([`api/src/common/mod.rs:51-58`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/api/src/common/mod.rs#L51-L58)).
- **Bounded waits that end in an error** where the hardware might never answer. The PWM's first-wrap wait gives up after at least two periods with `NoWrap` ([`pwm.rs:840-851`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L840-L851)), a fix the datasheet review asked for in rustos #2. The ADC gives up on `READY` after `READY_POLLS` reads ([`adc.rs:453-459`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/adc.rs#L453-L459)). How such a bound is computed without a timer is under [Bounding a wait without a timer](#bounding-a-wait-without-a-timer). Older waits are unbounded and say so (see [Known bugs, limits and flakes](#known-bugs-limits-and-flakes)).

The GPIO driver is the outlier: its `GpioError::PinOOB` is never returned and its `Debug` is written by hand ([`gpio.rs:45-87`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/gpio/gpio.rs#L45-L87)). Newer drivers derive.

### unsafe and its comments

- **Public methods are safe.** Register access sits in `unsafe { }` blocks inside them. A block holds a short run of register accesses with a plain `//` comment before each step that says what it does and why (for example [`pwm.rs:825-852`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L825-L852)).
- **Helpers that need a promise from the caller are `unsafe fn`** with a `# Safety` section in their doc that lists the promise: an index in range, a block out of reset, a pin owned by the caller ([`pwm.rs:818-822`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L818-L822), [`pwm.rs:886-891`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L886-L891), [`gpio.rs:363-369`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/gpio/gpio.rs#L363-L369)). Every public `unsafe fn` at master has one. Seven private ones in `clocks.rs` and `watchdog.rs` do not; see [Known bugs, limits and flakes](#known-bugs-limits-and-flakes).
- **`unsafe` also marks a broken ownership contract**, not only memory safety. `Rp2350Pwm::silence_all` is `pub unsafe fn` because it turns off outputs that other code owns, so it may be called only where no owner runs again: a panic or fault handler ([`pwm.rs:715-721`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L715-L721)).
- **`// SAFETY:` comments are rare** and sit directly above an `unsafe` item or call whose justification no `# Safety` doc already gives. At master the only one is on `unsafe impl Sync for Vector {}` ([`lib.rs:208-212`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/lib.rs#L208-L212)). #### Looking a citation up in `docs/extracted/rp2350-datasheet.md`

The file is the PDF run through `pdftotext -layout`; its header warns that line art and images do not survive and that anything load-bearing must be checked against the PDF ([`docs/extracted/rp2350-datasheet.md:3`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/docs/extracted/rp2350-datasheet.md#L3)). There are no page-break characters. Each page ends with a footer line (section title, then the printed page number), and the next line is the running header `RP2350 Datasheet`. So text that follows the footer numbered *N* is on printed page *N* + 1, which is PDF page *N* + 2.

```sh
# Find the item, then the last footer before it.
grep -n 'Table 1129\.' docs/extracted/rp2350-datasheet.md
#   80953:Table 1129. Mapping
awk -v at=80953 'NR < at && /^RP2350 Datasheet *$/ { f = prev } { prev = $0 } END { print f }' \
  docs/extracted/rp2350-datasheet.md
#   12.5. PWM   ...   1074      -> printed page 1075 = PDF page 1076
```

### Logic that can run on a computer goes in `api`

`firmware/pico2` has no tests at all: it is built only for its own target, `thumbv8m.main-none-eabihf` ([`Cargo.toml:4-7`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/Cargo.toml#L4-L7)), and nothing in it has `#[cfg(test)]`. So the rule is: **anything that does not need a register goes into `api`**, where `cargo test` runs it on the development machine, and the chip driver only moves bytes and applies the result.

- USB is the model. `api::usb` holds descriptors, the endpoint-0 request state machine, line coding, the byte ring and the zero-length-packet rules: "pure computation on bytes ... pinned down by the unit tests at the bottom of each file" ([`api/src/usb/mod.rs:1-8`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/api/src/usb/mod.rs#L1-L8)). `pico2::usb` is "the hardware half: it moves packets between the controller's dual-port RAM and that logic, and applies the `Effect`s it asks for" ([`usb/mod.rs:4-8`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/usb/mod.rs#L4-L8), [`usb/mod.rs:1036-1058`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/usb/mod.rs#L1036-L1058)). At master `api` has 35 `#[test]` functions in six USB files, and two doctests ([`api/src/usb/mod.rs:119-125`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/api/src/usb/mod.rs#L119-L125), [`api/src/usb/mod.rs:144-150`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/api/src/usb/mod.rs#L144-L150)). How to add a test is on [03 The api crate](03-api-crate.md).
- Multicore follows it on open PR #6: the core-1 launch handshake is a non-blocking state machine in `api::multicore`, tested against a model of core 1, and `pico2` supplies the `Mailbox` trait's implementation over the SIO FIFOs ([`api/src/multicore.rs:42-65`](https://github.com/robinonsay/rustos/blob/410dffa091e247e6e7546c7f2ff465f0af499d5a/api/src/multicore.rs#L42-L65), [`firmware/pico2/src/multicore.rs:220`](https://github.com/robinonsay/rustos/blob/410dffa091e247e6e7546c7f2ff465f0af499d5a/firmware/pico2/src/multicore.rs#L220); rustos PR #6, open, not on master). The pattern: a small trait in `api` for what the hardware does, the logic generic over it, a fake in the tests, the real one in `pico2`.
- **Arithmetic that is tied to the chip stays in `pico2` as `const fn`** and is checked when the crate builds with `const _: () = { .. assert!(..) .. };`. The PWM driver checks its pin-to-slice formula against Table 1129 typed in as data, and checks every integer frequency from 100 Hz to 20 kHz against its error bound ([`pwm.rs:355-381`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L355-L381), [`pwm.rs:496-529`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L496-L529)). A change that breaks the arithmetic fails the build. The watchdog keeps its reset-reason decision in a pure `const fn classify` "so the decision table is easy to check by reading" ([`watchdog.rs:429-431`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/watchdog.rs#L429-L431)).
- Where a check could not live in the repository, the PR says so. The ADC ring's overrun logic was checked in a separate model (400 seeds of 20 000 reads, per the rustos #5 description); that model is not in the repository.

`api` never depends on `pico2` and holds no register addresses ([`api/src/lib.rs:19-33`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/api/src/lib.rs#L19-L33)). Keep it that way: anything chip-specific in `api` breaks that rule.

### What rustos never uses

- **No outside crates.** "No external embedded crates (`cortex-m`, `cortex-m-rt`, `rp-hal`, `embassy`, …) are used; nothing outside this repository is compiled into the firmware image" ([`README.md:52-54`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/README.md#L52-L54)). `api` has no dependencies and `pico2` depends only on `api` ([`api/Cargo.toml:8`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/api/Cargo.toml#L8), [`firmware/pico2/Cargo.toml:6-7`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/Cargo.toml#L6-L7)), and the lockfile lists only those two packages ([`Cargo.lock:1-14`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/Cargo.lock#L1-L14)). Do not add one. A register crate or HAL would replace the cited, audited register code with code nobody here has read.
- **No interrupts.** Every driver is polled and leaves its block's interrupt enables at 0, and says so in its module doc ([`pwm.rs:194-196`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L194-L196), [`dma.rs:53-55`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/dma.rs#L53-L55), [`adc.rs:138-139`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/adc.rs#L138-L139), [`usb/mod.rs:216-217`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/usb/mod.rs#L216-L217)).
- **No heap.** Nothing in `firmware/pico2/src` uses `alloc` at master. Buffers are fixed-size fields or `&'static mut` statics the application provides, such as the ADC ring ([`adc.rs:477-483`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/adc.rs#L477-L483)).
- **No references to registers**, as above, and no `static mut` inside the drivers.
- **Inline assembly only for barriers and timing**: `dsb`/`isb` and `nop` through `core::arch::asm!` ([`lib.rs:262`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/lib.rs#L262), [`usb/hw.rs:337-339`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/usb/hw.rs#L337-L339)). That holds at master. ## How it connects

A driver has eight neighbours. Five hand it what it needs: the board (its handle), the chip-support helpers (base address and reset), the clocks (proof of order and frequencies), the GPIO layouts (pin routing) and the DMA (channel tokens). It gives three things out: implementations of the `api` traits, an off function for the fault and panic path, and, through a pinned rustos commit, code to cw-message-gateway's firmware.

## Algorithms and processing

### Constructor bring-up order

The PWM constructor shows the order a block driver follows ([`pwm.rs:614-625`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L614-L625)):

```rust
pub fn new(_handle: DeviceHandle<Rp2350Pwm>, _clocks: &Rp2350Clocks) -> Self {
    unsafe {
        clr_reset_reg(!RESET_IO_PADS);       // 1. shared blocks: release only
        wait_for_reset_done(RESET_IO_PADS);
        disconnect_pwm_pins();               // 2. undo what a warm reset left connected
        cycle_reset(RESET_PWM);              // 3. own block: full reset cycle
    }
    Self { claimed: 0, running: [None; SLICES] }
}
```

1. Release the shared blocks the driver needs, without asserting them.
2. Undo anything a previous run left that the block's reset will not undo (pins still routed to the block).
3. Cycle the driver's own block, so every register holds its documented reset value whatever ran before.
4. Configure, or leave configuration to the factory method if it depends on the request (the PWM programs a slice only when its first pin is claimed).
5. Wait only for what the datasheet says to wait for, with a bound and an error if the hardware can fail to answer.

### Safe start of an output

For an output that drives something outside the chip, the PWM sets the off level in the hardware before the pin is connected ([`pwm.rs:109-137`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L109-L137), [`pwm.rs:813-853`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L813-L853)):

1. Stop the slice, program `DIV` and `TOP`, write `CC` = 0 for both channels and `CTR` = 0.
2. Clear the wrap flag, start the slice, and poll `INTR` until it wraps. Give up after 2 × (period in `clk_sys` cycles + 1) reads, which is at least two periods; then stop the slice and return `NoWrap` with the pin never connected ([`pwm.rs:840-851`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L840-L851); the bound is explained [below](#bounding-a-wait-without-a-timer)).
3. After that wrap the double-buffered copies the output uses hold `CC` = 0, so the output is low by the datasheet's own rules.
4. Route the pin: pad, `FUNCSEL`, `ISO` last.

### Bounding a wait without a timer

A driver that waits for hardware bounds the wait by counting register reads, not by reading a clock, so it needs no timer value. The PWM's first-wrap wait:

```rust
// pwm.rs:840-842
// Each look at INTR takes at least one clk_sys cycle, so this many
// looks span at least two periods.
let looks = 2 * (config.period_sixteenths() / 16 + 1);
```

`period_sixteenths() / 16` is the slice's period in `clk_sys` cycles. Each `read_volatile` of `INTR` takes at least one `clk_sys` cycle, so the count converts to a minimum time: the loop cannot give up before two periods have passed, though it may run longer ([`pwm.rs:840-851`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L840-L851)). The USB driver bounds its `EP_ABORT_DONE` wait the same way, with `ABORT_SPIN_LIMIT = CLK_SYS_HZ / 20_000` iterations, "at least 3 cycles and in practice under 10" each, about 0.15-0.5 ms ([`usb/mod.rs:262-267`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/usb/mod.rs#L262-L267)). The ADC gives `READY` a fixed `READY_POLLS` = 100 000 reads ([`adc.rs:295`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/adc.rs#L295), [`adc.rs:453-459`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/adc.rs#L453-L459)).

The rule: derive a read count from the datasheet's worst case, so that the count is a lower bound on the time waited, and return an error when it runs out. Take `&Rp2350Timer` only when a real minimum time is the point, as USB does for its 10 ms disconnect pulse ([`usb/mod.rs:259-260`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/usb/mod.rs#L259-L260), [`usb/mod.rs:403`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/usb/mod.rs#L403)).

### Turning an output off

- **Normal path:** `write(false)` is one store through the clear alias; the change takes effect at the next counter wrap ([`pwm.rs:774-804`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L774-L804)).
- **Drop:** the same store, so an early return cannot leave a tone playing ([`pwm.rs:806-811`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L806-L811)).
- **Panic or fault:** `unsafe fn silence_all()` checks `is_reset_done(RESET_PWM)` and writes nothing while the block is still in reset; otherwise it clears `CC` on every slice and never stops a slice, because a stopped slice can hold a pin high ([`pwm.rs:696-728`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L696-L728)). The keyer firmware calls it from its `safe_state`, after opening the key and PTT lines ([`firmware/pico2-keyer/src/main.rs:236-251`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/src/main.rs#L236-L251)). **Never change this order:** the key and PTT open first, together, in one store, and `silence_all` comes second. That is a never-loosen safety rule of cw-message-gateway (the audit's KB-9), and its CI checks it in the built image with `check_faults.py` ([`firmware/pico2-keyer/check_faults.py:1-19`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/check_faults.py#L1-L19)); the full list of rules is the gateway's [13 Safety rules][gw-13].

### Build-time verification loops

`const` blocks can loop with `while` and call `const fn`s, so a table or a range can be checked exhaustively during the build:

```rust
// pwm.rs:500-518 (abridged): every accepted frequency has a configuration within its error bound
const _: () = {
    let mut hz = MIN_FREQUENCY_HZ;
    while hz <= MAX_FREQUENCY_HZ {
        let bound = if hz >= 300 && hz <= 3000 { TONE_ERROR_PPM } else { MAX_ERROR_PPM };
        match SquareConfig::for_frequency(CLK_SYS_HZ, hz) {
            Some(config) => { assert!(config.within_ppm(CLK_SYS_HZ, hz, bound)); /* .. */ }
            None => panic!("an accepted frequency has no PWM configuration"),
        }
        hz += 1;
    }
};
```

### Checklist for a new driver

1. Read the datasheet chapter; for every fact the code will rely on, note section, table and PDF page.
2. Add the block to `RegAddr` in address order, with its doc and "Base from §x, pN".
3. Create `firmware/pico2/src/<name>.rs` with the module doc first: `# Using it`, how the block works, the order of every sequence and why, `# Bring-up requirements` (reset bit, clock and its gate, `ACCESSCTRL` and any security register; see [Bring-up requirements](#bring-up-requirements-what-to-check-and-cite)), interrupts left off, and the page-number sentence.
4. Write the `#[repr(C)]` layouts with `_reserved` padding and `offset_of!` asserts; one documented constant per bit or field, with its citation.
5. Put pure arithmetic in `const fn`s and check it with `const` assertions; put protocol or state-machine logic in `api` with `#[cfg(test)]` tests and, if it needs hardware, a small trait the driver implements (how to add a test: [03 The api crate](03-api-crate.md)).
6. Define `<Name>Error` with `#[derive(Clone, Copy, Debug, PartialEq, Eq)]` and struct variants, or use `Infallible` where nothing can fail.
7. Write `pub fn new(_handle: DeviceHandle<Rp2350Name>, _clocks: &Rp2350Clocks) -> Self` (drop `_clocks` only if nothing depends on the clock tree; return `Result` if the hardware can refuse). Release shared blocks, `cycle_reset` your own, never touch bits 7 or 10.
8. Factory methods take `PinHandle<N>` or tokens by value and reference a `const` assert on `N`. Check every error before the first register write.
9. Access registers only through `&raw` pointers and `read_volatile`/`write_volatile`; use the set/clear aliases where a read-modify-write could race.
10. Route pins pad first, `FUNCSEL` second, `ISO` last, with the output already at its off level. Disconnect pins a warm reset left routed to your block.
11. Bound every wait that the hardware might not end, with a read count derived from the datasheet's worst case, and return an error.
12. If the driver drives anything outside the chip, make `Drop` put it in its off state, and provide an `unsafe fn` that does the same without driver values, guarded by `is_reset_done`, for the application to call from its `safe_state` (which the fault handlers run through `entry!`) and from its own panic handler.
13. Give every `unsafe fn` a `# Safety` section; comment each step inside `unsafe` blocks.
14. Add the device to `define_board!` in `board.rs` (the `use`, the `devices` line, the module doc's handle list and bring-up order), `pub mod` in `lib.rs` (and its layering note), and the driver list in `README.md`. In `lib.rs` change nothing else: the fault handlers' first call is a never-loosen rule (see [Changing it](#changing-a-driver-or-an-api-trait)).
15. Implement the `api` traits that fit (`ErrorType`, `Write<T>`, `Read<T>`, or a peripheral trait).
16. No new dependencies, no interrupts, no heap.
17. Run the checks below; write "Not run on hardware" in the commits and the PR if it has not been.
18. Open the PR against `master` with the description shape under [Pull request conventions](#pull-request-conventions).

## Changing it

### Changing a driver or an `api` trait

- **`api` is the portability boundary.** A change to a trait in `api::common` or `api::gpio` changes every implementor and every application written against it. Add a new trait or method rather than change a signature, and say in the PR who is affected.
- **A public signature in `pico2` is used by cw-message-gateway's firmware**: the keyer firmware on main, and the decoder firmware on cw-message-gateway PR #30 (open, not on main). Renaming or changing it breaks their build at their next pin move, not at once (they pin a commit). Search their sources, and the check scripts below, for the name before changing it.
- **Keep the citations true.** When behaviour changes, change the module doc and the cited section, table and page in the same commit. If a fact turns out to be wrong in the datasheet, say so in the doc, as `pwm.rs:55-57` does.
- **Do not weaken an off path.** `Drop`, `silence_all`, the zero-before-connect start and the warm-reset disconnect exist because the keyer box drives a radio. A change to any of them is a change to what cw-message-gateway's safety rules rely on; read [13 Safety rules][gw-13] first and expect the audit to check it.
- **The fault path is a never-loosen rule.** Do not add work before the `__rustos_safe_state()` call in `OnHardFault` or `DefaultHandler`, do not rename those handlers, and do not change what `entry!` generates ([`lib.rs:395-415`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/lib.rs#L395-L415), [`lib.rs:447-469`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/lib.rs#L447-L469)); see [02 Boot and runtime](02-boot-runtime.md). The keyer box's rule that the key line is open in the fault handlers depends on it. cw-message-gateway's CI checks the built keyer image with `check_faults.py`, which finds `OnHardFault`, `DefaultHandler` and the panic handler by symbol name ([`firmware/pico2-keyer/check_faults.py:41`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/check_faults.py#L41)). The decoder box's `check_pins.py` (PR #30, open, not on main) and the one-Pico image's `check_core1.py` (PR #31, draft, not on main) also find rustos items by name, such as `multicore::core1_start` and `CORE1_STACK_LIMIT` ([`firmware/pico2-keyer/check_core1.py:71-96`](https://github.com/robinonsay/cw-message-gateway/blob/bc5062ae4f56ae1f9949b3b067218c7e675d88f8/firmware/pico2-keyer/check_core1.py#L71-L96)). Before renaming or moving anything on that path, search those scripts as well as the firmware sources.
- **Never add a file named `Cargo.toml` that is not a real package** (an example or a template). cargo reads every `Cargo.toml` in a git dependency's repository, so every dependent's build would print an error; that is why template manifests are named `Cargo.toml.liquid` ([`templates/README.md:31-35`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/templates/README.md#L31-L35)). The fix was rustos #4, and its pin move is the case described below.
- **Tests to update:** for `api`, the unit tests at the bottom of the file you change (USB descriptor bytes are pinned exactly, so a descriptor change must change its test); for `pico2`, the `const` assertions next to the arithmetic you change.

### How cw-message-gateway picks up a rustos change

cw-message-gateway's firmware does not follow rustos's `master`. It names a commit:

```toml
# firmware/pico2-keyer/Cargo.toml:30-31 at cw-message-gateway main 44185fa
api = { git = "https://github.com/robinonsay/rustos", rev = "8c915079996f9d6537a1ec1f56dc5e3ea5cccc4c" }
pico2 = { git = "https://github.com/robinonsay/rustos", rev = "8c915079996f9d6537a1ec1f56dc5e3ea5cccc4c" }
```

([`firmware/pico2-keyer/Cargo.toml:21-31`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/Cargo.toml#L21-L31).) A rustos change reaches the box only when that line moves, and moving it can change the firmware image even with no source change, because cargo mixes the git revision into the hash in every symbol name and the code's layout follows those names ([`firmware/pico2-keyer/Cargo.toml:27-29`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/Cargo.toml#L27-L29)). The measured case, the compiler pin and every pin in use are on [08 Changes made for cw-message-gateway](08-changes-for-cw-gateway.md); the chain from a rustos merge to a flashed box, with its figure, is on [09 Work left and known issues](09-work-left-known-issues.md). What a driver author must know:

- **Any rustos change a firmware image picks up, however small, and any pin move, even one with no source change, goes back through cw-message-gateway's safety audit** before anything built from it is flashed. A different image has a different hash, and when the image does come out identical, the pin bump is still a PR the audit checks. There is no exception and no shortcut; [14 Audit, bench and flashing][gw-14] describes the process and [08 Keyer box: firmware][gw-08] the firmware.
- **The pin bump is its own cw-message-gateway PR** (for rustos #4 it was cw-message-gateway #24), so the audit sees exactly which rustos commit the image is built from.
- **The firmware pins a rustos branch commit only until the rustos PR merges, then its merge commit on `master`** ([`firmware/pico2-keyer/README.md:16-17`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/README.md#L16-L17)). Merging with a merge commit, as every merged rustos PR was, keeps the pinned branch commit reachable from `master`; a squash merge would not (rustos #3's description).

- **Some waits are unbounded and documented as such**: `wait_for_reset_done` ([`reset.rs:196-199`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/reset.rs#L196-L199)), the crystal and PLL-lock waits in `Rp2350Clocks::new` (documented at [`clocks.rs:378-382`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/clocks.rs#L378-L382); the loops are at [`clocks.rs:458`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/clocks.rs#L458) and [`clocks.rs:483`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/clocks.rs#L483)), the ADC stream's `Drop` ([`adc.rs:670-682`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/adc.rs#L670-L682)) and `dma::abort` ([`dma.rs:280-281`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/dma.rs#L280-L281)).
- **No CI**, and 13 clippy findings in `gpio.rs`, `gpio/mod.rs` and `lib.rs` that predate the drivers this project added (rustos #1 and #3 descriptions).
- **Little has run on hardware.** No rustos PR was run on hardware before it merged (the #1, #2, #3, #5 and #6 descriptions say so; #4 changed only template files). Since then, the keyer box image built as `eef8c126`, on rustos `c985211` (whose `api` and `pico2` sources are those of `8c91507`), has been flashed onto a Pico 2 on the Quansheng bench with no radio connected. It boots, which runs the GPIO, clocks, PWM (including the first-wrap wait for GP18), timer, SysTick, watchdog and USB bring-up ([`firmware/pico2-keyer/src/main.rs:176-204`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/src/main.rs#L176-L204) in cw-message-gateway; the same calls as in the flashed build), enumerates over USB and answers `hfnode keyer check` with its build and the audited limits (project file `bench/quansheng.md`, stage 2; [08 Changes made for cw-message-gateway](08-changes-for-cw-gateway.md)). Nothing has been keyed, and no driver has been measured with instruments. The ADC and DMA (rustos #5) and multicore (rustos #6) code has not run on hardware. Behaviour the datasheet leaves open is still marked "Unverified on hardware" in the code, for example the USB clear alias on write-1-to-clear flags ([`usb/hw.rs:112-119`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/usb/hw.rs#L112-L119)).
- **One SysTick driver per board.** SysTick registers are per core and `Rp2350SysTick` drives the SysTick of the core that calls `new` ([`systick.rs:41-43`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/systick.rs#L41-L43)), but the board has one `systick` handle ([`common/board.rs:138`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/board.rs#L138)). On rustos PR #6, core 1 cannot get a SysTick driver value in safe code.
- **"Within two periods" in two PWM docs.** The `NoWrap` variant's doc, the factory's error list and `start_slice`'s doc say the slice "did not wrap within two periods" ([`pwm.rs:568`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L568), [`pwm.rs:651-652`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L651-L652), [`pwm.rs:815-816`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L815-L816)); the code reads `INTR` enough times to span at least two periods and may wait longer, as the module doc and the loop's comment say ([`pwm.rs:123-125`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L123-L125), [`pwm.rs:840-842`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L840-L842)). The code is right; the three docs are loose.
- **The extracted datasheet is lossy**: tables that are images and the PWM's period equations (typeset images, [`pwm.rs:63-64`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L63-L64)) are missing from it. Check those in the PDF.

The full list for the repository is on [09 Work left and known issues](09-work-left-known-issues.md).

## Work left

- **rustos PR #6** (multicore and `Rp2350Usb::room()`) is open; see [06 Multicore](06-multicore.md).
- **Fix the README and the doc comments listed above.** None of these change code behaviour, but any rustos commit a firmware image picks up still means a new pin and a new audit pass.
- **Make the GPIO pin-range asserts effective**, by referencing them as the PWM does, or remove them.
- **Add `# Safety` sections** to the seven private `unsafe fn`s.
- **No CI exists for rustos.** The checks above are run by hand.
- **Drivers that do not exist at `80bf599`**: no UART, SPI, I2C or PIO driver. `docs/icd/rp2350/` has interface notes for clocks, GPIO, UART, I2C and SPI, "tailored for the Juno FSW driver code" as its index says ([`docs/icd/rp2350/index.md:5-13`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/docs/icd/rp2350/index.md#L5-L13)); no driver here implements UART, SPI or I2C. A UART or SPI driver would run on `clk_peri` (`CLK_PERI_HZ`); an I2C driver runs on `clk_sys` (`CLK_SYS_HZ`), per §12.2.1.2, p982. The facts an I2C driver starts from are under [Starting an I2C driver](#starting-an-i2c-driver).
- **No rustos API for a block's or a DMA channel's security level** (`ACCESSCTRL`, `SECCFG_CHn`). The one-Pico image writes `SECCFG_CH0` itself; a rustos option is optional later work, and any change to that path is a change to an audited image ([08 Changes made for cw-message-gateway](08-changes-for-cw-gateway.md), [09 Work left and known issues](09-work-left-known-issues.md)).
- **Hardware checks waiting for Robin's go**, such as rustos #2's scope checks (on and off at 100 Hz and 20 kHz; a watchdog reset with a tone on).
