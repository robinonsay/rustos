# 04 Drivers: core (board, clocks, time, watchdog)

> The core of rustos's `pico2` crate: the board singleton that hands out every pin and peripheral exactly once, the table of register base addresses, the reset-controller helpers every driver calls, and the four drivers that give the chip an accurate clock, a sense of time and a way to recover from a hang. `Rp2350Clocks` moves the RP2350 from its drifting internal oscillator onto the 12 MHz crystal and two PLLs (150 MHz system clock, 48 MHz USB clock). `Rp2350Timer` is a 64-bit microsecond counter that no debugger can pause. `Rp2350SysTick` is a second, independent count of processor cycles, so that software can notice when the microsecond count has stopped. `Rp2350Watchdog` resets the chip when the program stops feeding it, keeps two words of application state across that reset, and tells the next boot why it restarted. The keyer box firmware in cw-message-gateway uses all of them for its safety limits. Everything here is at rustos master `80bf599`. The clocks, timer, SysTick and watchdog drivers were written for the cw-message-gateway project: `clocks.rs`, `timer.rs`, `watchdog.rs`, `cycle_reset` and the clocks, timer, watchdog and USB device handles in rustos #1 (`f013570`, `929a5a0`, `5bb9199`); `is_reset_done` in #2 (`c1c82c9`); `systick.rs`, `DBGPAUSE` = 0 and the scratch registers in #3 (`02b762b`); the `clk_adc`, ADC and DMA entries in #5 (`5123db5`). The board, the `RegAddr` map and the reset helpers in `firmware/pico2/src/common/`, and `define_board!` in `api/src/device/mod.rs`, are Robin's (the project owner's) earlier work, which those PRs extended; [08 Changes for cw-message-gateway](08-changes-for-cw-gateway.md) tells that history. The keyer image built on these drivers has run on a bare Pico 2 (clocks, timer, SysTick, watchdog start and feed), but no reset, debugger or fault path has run on a chip ([What has run on a chip](#what-has-run-on-a-chip); [09 Work left and known issues](09-work-left-known-issues.md), W4).

Terms used on this page, in plain words (the shared glossary is the [cw-message-gateway glossary](https://github.com/robinonsay/cw-message-gateway/blob/claude/handover-docs-us00cn/docs/handover/17-glossary.md)):

- **Register**: a 32-bit word at a fixed address that controls a hardware **block** (a peripheral such as the timer). **Reset** has two meanings: a block held in reset by the chip's reset controller, and a reset of the whole chip.
- **XOSC**: the crystal oscillator, which turns the 12 MHz quartz crystal on the board into an accurate clock. **ROSC**: the ring oscillator inside the chip, which needs no crystal but drifts with voltage and temperature.
- **PLL** (phase-locked loop): a circuit that multiplies a reference clock up to a high frequency in its **VCO** (voltage-controlled oscillator) and then divides it down with **post dividers**.
- **Clock generator**: one of the chip's named clocks (`clk_ref`, `clk_sys`, `clk_peri`, `clk_usb`, `clk_adc`), each a **mux** (multiplexer, a switch that picks the source) plus a divider. A **glitch** is a malformed clock pulse that can corrupt logic.
- **Tick**: a once-per-microsecond pulse made by dividing `clk_ref`; the timer and watchdog count ticks, not clock cycles. **SysTick**: the 24-bit countdown timer built into each Arm Cortex-M33 core.
- **Watchdog**: a countdown that resets the chip when it reaches zero; the program **feeds** it (reloads it) to show it is still running. **Scratch registers**: watchdog words that keep their value through a watchdog reset.
- **PSM** (power-on state machine): the hardware sequencer that brings the chip up stage by stage; a watchdog reset re-runs it. **POWMAN**: the power manager, which records the cause of the last chip-level reset. **Bootrom**: the code in the chip's ROM that runs first after every reset.
- **Pad**: the electrical driver behind a pin; its **isolation latch** (`ISO` bit) can freeze the pin's state.
- **Keyer box**: the Pico 2 in cw-message-gateway that keys a radio's transmitter by closing its **key line**; **CW** is Morse code sent that way. **PTT** (push-to-talk): the line that switches a radio to transmit.
- **Trip**: the keyer box's latched fault state, in which it opens its outputs and refuses to key until it is power-cycled. **Duty budget**: the keyer's allowance of transmit time, spent while keyed and earned back while not. **`TEST HANG`**: a keyer test command that stops the control loop on purpose so that the watchdog must reset the box.
- **UF2**: the file format the bootrom's USB drive accepts for flashing; **picotool** is Raspberry Pi's command-line tool that loads and reboots a Pico. **QMI**: the interface that streams code from the external flash chip.
- **RUN pin**: the chip's external reset pin. **Brown-out**: the supply voltage dipping below the chip's minimum, which resets it.

## How it works

### Bring-up order

An application claims the board once, then turns device handles into drivers in an order the types enforce: every driver that depends on a frequency takes `&Rp2350Clocks` as proof that the clock tree is set up, and USB also takes `&Rp2350Timer` ([`firmware/pico2/src/common/board.rs:20-33`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/board.rs#L20-L33)). The keyer box shows the order a safety-critical application uses ([`firmware/pico2-keyer/src/main.rs:174-234`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/src/main.rs#L174-L234)):

1. `Rp2350::take()`: the only way safe code gets handles (the `unsafe` `PinHandle::new` and `DeviceHandle::new` bypass it, [`api/src/device/mod.rs:95`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/api/src/device/mod.rs#L95), [`api/src/device/mod.rs:159`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/api/src/device/mod.rs#L159); see [03 The api crate](03-api-crate.md)).
2. GPIO first: the key and PTT pins are driven low before anything else, because a pin's state across resets depends on the pad latches (see [GPIO pins across a watchdog reset](#gpio-pins-across-a-watchdog-reset)). The clocks driver's own doc says to call `Rp2350Clocks::new` "first, before any other driver" and assumes "no GPIO has been configured" ([`firmware/pico2/src/clocks.rs:378-382`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/clocks.rs#L378-L382)). That sentence is stale: `Rp2350Gpio::new` takes no clock proof ([`firmware/pico2/src/gpio/gpio.rs:132-139`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/gpio/gpio.rs#L132-L139)), and safety outputs must come first, as the watchdog's own "Typical use" ([`firmware/pico2/src/watchdog.rs:185-199`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/watchdog.rs#L185-L199)) and the keyer do. Follow this order, not that sentence.
3. `Rp2350Clocks::new`: the crystal, both PLLs and four clock generators. Everything after this runs at 150 MHz.
4. PWM, `Rp2350Timer::new`, `Rp2350SysTick::new`, `Rp2350Watchdog::new` (which only reads the reset evidence; it does not start the watchdog).
5. USB, which blocks for about 10 ms while it signals a fresh attach ([`firmware/pico2/src/usb/mod.rs:52-54`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/usb/mod.rs#L52-L54)).
6. `watchdog.start(timeout)`, then the main loop, which feeds it on every pass.

### The board and its handles

`board.rs` is one invocation of the `api` crate's `define_board!` macro ([`firmware/pico2/src/common/board.rs:97-146`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/board.rs#L97-L146)). It generates `Rp2350Pins` (one zero-sized `PinHandle<N>` per pin), the `Rp2350` struct (the pins plus one zero-sized `DeviceHandle<T>` per device), and `Rp2350::take() -> Option<Rp2350>`, which flips a static `AtomicBool` with one `compare_exchange` so that exactly one caller per boot, on either core, gets `Some` ([`api/src/device/mod.rs:314-319`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/api/src/device/mod.rs#L314-L319)). After that, ownership is enforced by moves: each driver constructor takes its handle by value, so a second driver for the same block does not compile. How the macro and the handle types work is on [03 The api crate](03-api-crate.md); this page lists what the Pico 2 board declares.

Field names say what is safe to wire to. `gpio0` to `gpio22` and `gpio26` to `gpio28` are free pins on the 40-pin header; four pins are already committed to the board's own circuits and carry that name instead: `smps_ps` (GP23, the regulator's power-save select), `vbus_sense` (GP24, high when USB power is present), `led` (GP25, the on-board LED) and `vsys_adc` (GP29, reads the supply voltage divided by three) ([`firmware/pico2/src/common/board.rs:65-74`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/board.rs#L65-L74)). `MAX_GPIO_PIN` = 30 records that the RP2350A package on the Pico 2 bonds out GPIO0 to 29, although the register map has room for 48 pins and a write to pin 40 silently succeeds ([`firmware/pico2/src/common/mod.rs:13-40`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/mod.rs#L13-L40)).

### Registers and the atomic aliases

`RegAddr` is a `#[repr(usize)]` enum whose variants are the base addresses of the blocks rustos drives, named as the datasheet names them ([`firmware/pico2/src/common/reg.rs:52-57`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/reg.rs#L52-L57)), with one exception: the variant `RESET` is the datasheet's `RESETS` block ([`firmware/pico2/src/common/reg.rs:72-74`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/reg.rs#L72-L74)). A driver casts a variant to a pointer to its own `#[repr(C)]` layout struct and reaches each register with `&raw mut (*p).field` and a volatile read or write ([`firmware/pico2/src/common/reg.rs:3-15`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/reg.rs#L3-L15)).

Every peripheral block is given 4 KB of address space and is mirrored three more times; a write through a mirror changes only the bits written ([`firmware/pico2/src/common/reg.rs:29-51`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/reg.rs#L29-L51); datasheet §2.1.3, [`docs/extracted/rp2350-datasheet.md:1573-1600`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/docs/extracted/rp2350-datasheet.md#L1573-L1600)):

| Address | A write of `v` does |
|---|---|
| base + `0x0000` | normal write: the register becomes `v` |
| base + `0x1000` | atomic XOR: the register becomes `reg ^ v` |
| base + `0x2000` | atomic set: the register becomes `reg \| v` |
| base + `0x3000` | atomic clear: the register becomes `reg & !v` |

The aliases change one field in a single bus write, with no read-modify-write window in which an interrupt handler or the other core could slip in. Among the regions without them, three are ones rustos touches. The SIO block (single-cycle I/O at `0xd000_0000`, which has its own `SET`/`CLR`/`XOR` registers) and the Arm core's own registers on the private peripheral bus, such as SysTick, are both in §2.1.3's exclusion list, which also excludes the CoreSight debug window and the OTP programming registers ([`docs/extracted/rp2350-datasheet.md:1592-1601`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/docs/extracted/rp2350-datasheet.md#L1592-L1601); [`firmware/pico2/src/common/reg.rs:50-51`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/reg.rs#L50-L51)). The USB controller's dual-port RAM has none either (§12.7.3.7, [`docs/extracted/rp2350-datasheet.md:86099-86102`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/docs/extracted/rp2350-datasheet.md#L86099-L86102); [`firmware/pico2/src/common/reg.rs:133-137`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/reg.rs#L133-L137)).

`reg.rs` holds addresses and documentation only; it has no access functions. A driver that uses an alias builds the alias pointer itself, as the PWM driver does with `pwm_set()` and `pwm_clr()` ([`firmware/pico2/src/pwm.rs:270-285`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L270-L285)) and the USB driver with `regs_set()` and `regs_clr()` ([`firmware/pico2/src/usb/hw.rs:101-122`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/usb/hw.rs#L101-L122)). The keyer firmware's fault path does the same with raw addresses: it opens the key and PTT with one write to SIO `GPIO_OUT_CLR`, and holds the tone pin low through the `IO_BANK0` clear and set aliases ([`firmware/pico2-keyer/src/main.rs:254-277`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/src/main.rs#L254-L277)). No rustos code writes through the `+0x1000` XOR alias. The USB driver also writes its write-1-to-clear flags through the clear alias, as the datasheet's own USB example does; how a clear-alias write meets such a flag is not spelled out in the datasheet and is unverified on hardware ([`firmware/pico2/src/usb/hw.rs:112-121`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/usb/hw.rs#L112-L121)).

Background: the repository's tutorial explains volatile access, read-modify-write and the aliases in [chapter 07](../tutorials/rp2350_baremetal/07_registers_and_bits.md) (§7.1-7.6), and writes `reg.rs` and `reset.rs` step by step in [chapter 08](../tutorials/rp2350_baremetal/08_first_blink.md) (§8.3-8.5). The tutorial predates the current workspace layout ([09 Work left and known issues](09-work-left-known-issues.md), W5), so where it and the code differ, trust the code.

### The reset controller

Almost every block starts held in reset and does nothing until software releases it (datasheet §7.5.1, [`docs/extracted/rp2350-datasheet.md:36562`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/docs/extracted/rp2350-datasheet.md#L36562)). The `RESETS` block has three registers, all with one bit per block in the same positions (Table 534, [`firmware/pico2/src/common/reset.rs:19-34`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/reset.rs#L19-L34)):

- `RESET` (offset `0x0`, reset value `0x1fff_ffff`): **1 holds a block in reset, 0 releases it** ([`firmware/pico2/src/common/reset.rs:37-62`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/reset.rs#L37-L62)).
- `WDSEL` (`0x4`): blocks to reset when the watchdog fires. rustos never writes it ([`firmware/pico2/src/common/reset.rs:63-75`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/reset.rs#L63-L75)).
- `RESET_DONE` (`0x8`, read-only): **1 means the block is out of reset and ready**, the opposite polarity of `RESET` ([`firmware/pico2/src/common/reset.rs:76-93`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/reset.rs#L76-L93)).

### The clock tree

Out of reset the RP2350 runs from the ROSC, roughly 11 MHz: the power-on state machine runs `clk_ref` from the ROSC and `clk_sys` from `clk_ref`, then the bootrom moves `clk_sys` onto the ROSC through its aux mux and may change dividers. So when `Rp2350Clocks::new` starts, `clk_ref` and `clk_sys` both run from the ROSC ([`firmware/pico2/src/clocks.rs:4-12`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/clocks.rs#L4-L12)). That is not accurate enough for USB, which needs exactly 48 MHz, or for a microsecond timer. `Rp2350Clocks::new` replaces it with the tree in the figure.

![The clock tree as Rp2350Clocks::new sets it up: the 12 MHz crystal oscillator feeds clk_ref at 12 MHz and both PLLs; PLL_SYS gives clk_sys and clk_peri at 150 MHz, PLL_USB gives clk_usb at 48 MHz and, once the ADC driver starts it, clk_adc at 48 MHz; the right-hand column names the rustos drivers that rely on each clock](diagrams/04-clock-tree.svg)

*Figure: every frequency the drivers compute with comes from this tree; notice that `clk_ref` (and so every microsecond tick) comes straight from the crystal, while `clk_sys` (and so SysTick) goes through `PLL_SYS`.*

The values ([`firmware/pico2/src/clocks.rs:89-118`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/clocks.rs#L89-L118), [`firmware/pico2/src/clocks.rs:171-175`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/clocks.rs#L171-L175)):

| Clock | Source | Setting | Frequency |
|---|---|---|---|
| XOSC | 12 MHz crystal | `FREQ_RANGE` 1-15 MHz, start-up delay 282 × 256 crystal cycles (6 ms) | 12 MHz |
| `PLL_SYS` | XOSC | `REFDIV` 1, `FBDIV` 125, `POSTDIV1` 5, `POSTDIV2` 2: VCO 1500 MHz | 150 MHz |
| `PLL_USB` | XOSC | `REFDIV` 1, `FBDIV` 100, `POSTDIV1` 5, `POSTDIV2` 5: VCO 1200 MHz | 48 MHz |
| `clk_ref` | XOSC, glitchless `SRC` = 2 | divide by 1 | 12 MHz |
| `clk_sys` | aux mux = `PLL_SYS`, glitchless `SRC` = 1 (aux) | divide by 1 | 150 MHz |
| `clk_peri` | aux mux = `clk_sys` | divide by 1 | 150 MHz |
| `clk_usb` | aux mux = `PLL_USB` | divide by 1 | 48 MHz |
| `clk_adc` | aux mux = `PLL_USB`, started by the ADC driver | divide by 1 | 48 MHz |

The PLL values are the SDK defaults the datasheet gives for the RP2350 (§8.6.4, [`docs/extracted/rp2350-datasheet.md:42543-42546`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/docs/extracted/rp2350-datasheet.md#L42543-L42546)). 150 MHz is the RP2350's rated system clock and 48 MHz is required for both USB and the ADC (Table 540, [`docs/extracted/rp2350-datasheet.md:37686-37716`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/docs/extracted/rp2350-datasheet.md#L37686-L37716)). `clk_hstx` and the four `clk_gpout` generators are left alone ([`firmware/pico2/src/clocks.rs:68-71`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/clocks.rs#L68-L71)). Code runs from flash at `clk_sys` divided by the QMI divisor the bootrom picked, which is at least 3, so the flash clock is at most 50 MHz; `clocks.rs` does not reprogram the QMI ([`firmware/pico2/src/clocks.rs:73-79`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/clocks.rs#L73-L79)).

Every clock generator has an **aux mux**, which glitches if switched while running. `clk_ref` and `clk_sys`, the two clocks that may never stop, also have a **glitchless mux** in front of the aux mux, with a `SELECTED` register that confirms the switch (§8.1.2.2, [`docs/extracted/rp2350-datasheet.md:37735-37791`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/docs/extracted/rp2350-datasheet.md#L37735-L37791)). The driver implements the datasheet's three recipes as three functions, and the divisor-ordering rule from the SDK's `clock_configure` (a larger divisor goes in before the source changes, a smaller one after, so the output never runs faster than either setting) ([`firmware/pico2/src/clocks.rs:28-49`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/clocks.rs#L28-L49)). The step-by-step sequence is under [Algorithms and processing](#clock-bring-up-rp2350clocksnew).

### Time: the tick, TIMER0 and SysTick

The timers do not count a clock directly. The `TICKS` block divides `clk_ref` by a programmable cycle count and sends one tick per period to each of six destinations (both cores' SysTicks, `TIMER0`, `TIMER1`, the watchdog, the RISC-V platform timer), each with its own generator that resets **disabled**; a timer whose generator is off never counts ([`firmware/pico2/src/timer.rs:3-17`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/timer.rs#L3-L17); §8.5.1, [`docs/extracted/rp2350-datasheet.md:41714-41752`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/docs/extracted/rp2350-datasheet.md#L41714-L41752)). With `clk_ref` at 12 MHz, a count of 12 gives one tick per microsecond, so `TICK_CYCLES` = 12 ([`firmware/pico2/src/timer.rs:67-70`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/timer.rs#L67-L70)). `Rp2350Timer::new` starts the `TIMER0` generator; `Rp2350Watchdog::start` starts the watchdog's own, rather than trusting anything else to.

`TIMER0` counts those ticks in 64 bits, from 0 when `Rp2350Timer::new` releases it from reset. At 1 MHz the count cannot wrap in practice (about 584,000 years), so the driver treats it as never wrapping ([`firmware/pico2/src/timer.rs:163-174`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/timer.rs#L163-L174)). It reads the two raw halves without the latching register pair, so that both cores and interrupt handlers can read it at once (§12.8.4.1, [`docs/extracted/rp2350-datasheet.md:89031-89063`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/docs/extracted/rp2350-datasheet.md#L89031-L89063)).

**Never paused by a debugger.** `TIMER0`'s `DBGPAUSE` bits reset to 1, which stops the count while a debugger halts either core. A debugger that halts core 1 would then freeze the time core 0 reads while core 0 runs on and keeps feeding the watchdog: every deadline measured on the timer would stop coming due. For a device that keys a transmitter that is a key-down limit that never expires, so `Rp2350Timer::new` writes `DBGPAUSE` = 0 ([`firmware/pico2/src/timer.rs:42-56`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/timer.rs#L42-L56); Table 1238, [`docs/extracted/rp2350-datasheet.md:89543-89555`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/docs/extracted/rp2350-datasheet.md#L89543-L89555)). The cost: time runs on while you single-step.

**SysTick, the second witness.** Everything above counts the one microsecond tick: anything that stops it (its generator disabled, `TIMER0` paused or held in reset, `clk_ref` stopped) stops every deadline at once while the code that should notice keeps running. Each core's SysTick can instead count the processor clock, `clk_sys`, which shares none of that path ([`firmware/pico2/src/systick.rs:4-17`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/systick.rs#L4-L17)). `Rp2350SysTick::new` runs it free on `clk_sys` with the largest reload value and no interrupt; it wraps every 2^24 cycles, about 112 ms at 150 MHz ([`firmware/pico2/src/systick.rs:26-39`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/systick.rs#L26-L39)). Software that reads both counts can tell when the microsecond tick has stopped while the processor has not; the keyer box does exactly that every 50 ms (see [How the keyer firmware uses each part](#how-the-keyer-firmware-uses-each-part)).

**The watchdog counts the same kind of tick.** It has its own `TICKS` generator, but on the same `clk_ref` ([`firmware/pico2/src/systick.rs:6-11`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/systick.rs#L6-L11), [`firmware/pico2/src/watchdog.rs:19-24`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/watchdog.rs#L19-L24)). So a stopped `clk_ref` or crystal also stops the watchdog: it cannot reset a chip whose reference clock has died. On the keyer box the clock check then opens the key and PTT itself and trips (`CLOCK`) ([`crates/keyer-core/src/control.rs:86-136`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/crates/keyer-core/src/control.rs#L86-L136), [`crates/keyer-core/src/control.rs:408-412`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/crates/keyer-core/src/control.rs#L408-L412)), but only as long as `clk_sys` still runs. `clk_ref` and `clk_sys` both descend from the crystal, and what `clk_sys` does if the crystal stops is not stated in the datasheet; if the processor clock stops, no software can notice ([`firmware/pico2/src/systick.rs:19-24`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/systick.rs#L19-L24)).

### The watchdog

![The watchdog's life cycle: new reads the reset evidence, start arms a timeout, every loop pass saves state and feeds; if the loop stops the counter reaches zero and a system-level reset restarts both cores while REASON and the scratch registers survive; on the next boot new classifies the reason and the application reads its scratch registers back](diagrams/04-watchdog-reset.svg)

*Figure: the reset is a system-level one, so the watchdog's own registers (the reason, the scratch words, the marker) survive it, and the next boot can tell a timeout from a power-up; a chip-level reset (right) erases them.*

The watchdog's counter is `CTRL.TIME`, loaded from `LOAD`, counting down once per microsecond tick, up to `0xff_ffff` = 16 777 215 µs, about 16.78 s (the code's comment truncates it to 16.7 s) ([`firmware/pico2/src/watchdog.rs:13-15`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/watchdog.rs#L13-L15)). Feeding is writing `LOAD` again. The RP2040's erratum that made its watchdog count twice per tick has no RP2350 counterpart, so one tick is one count ([`firmware/pico2/src/timer.rs:31-40`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/timer.rs#L31-L40); unverified on hardware).

**What a watchdog reset resets.** The watchdog only raises the event; three registers outside it decide how much of the chip it tears down ([`firmware/pico2/src/watchdog.rs:26-63`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/watchdog.rs#L26-L63); §12.9.4, [`docs/extracted/rp2350-datasheet.md:89753-89762`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/docs/extracted/rp2350-datasheet.md#L89753-L89762)):

| Register | Level | rustos sets |
|---|---|---|
| `POWMAN.WDSEL` | chip level: also reset the power manager or the switched-core power domain | 0: never used |
| `PSM.WDSEL` | system level: re-run the power-on state machine from chosen stages | every stage except `ROSC` and `XOSC` |
| `RESETS.WDSEL` | subsystem level: reset single blocks | untouched: the `RESETS` stage already resets every block |

`PSM.WDSEL` resets to 0, so a watchdog with the default scope would expire and reset nothing; rustos selects every stage but the two oscillators, as the SDK does, so both cores restart through the bootrom and every block comes back held in reset. The chip-level options stay off on purpose, because a chip-level reset also resets the watchdog block and with it the reason register and the scratch registers. `SYSCFG.AUXCTRL` bit 0 is set too, because the datasheet says it "must be set before initiating a watchdog reset of the RSM from a stage that includes CLOCKS" when the power manager runs from `clk_ref` (Table 1316, [`docs/extracted/rp2350-datasheet.md:94305-94328`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/docs/extracted/rp2350-datasheet.md#L94305-L94328)); since a timeout can come at any time after `start`, the bit is set there and left set.

**Pause bits.** `CTRL.PAUSE_DBG0`, `PAUSE_DBG1` and `PAUSE_JTAG` reset to 1, which freezes the countdown while a debugger halts a core. `start` clears all three, so a debugger cannot hold a keyed transmitter keyed by halting the core ([`firmware/pico2/src/watchdog.rs:65-75`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/watchdog.rs#L65-L75)). The cost is that single-stepping with the watchdog running resets the chip. For a development application that is not the keyer image, a debug session can leave the watchdog unstarted or give it a long timeout ([`firmware/pico2/src/watchdog.rs:72-74`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/watchdog.rs#L72-L74)). **The keyer box's `WATCHDOG_MS` = 500 ms is a never-loosen limit** ([`crates/keyer-core/src/lib.rs:61-62`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/crates/keyer-core/src/lib.rs#L61-L62)): it is never changed for debugging, and only the audited image is ever flashed to a box ([13 Safety rules](https://github.com/robinonsay/cw-message-gateway/blob/claude/handover-docs-us00cn/docs/handover/13-safety-rules.md), [14 Audit, bench and flashing](https://github.com/robinonsay/cw-message-gateway/blob/claude/handover-docs-us00cn/docs/handover/14-audit-bench-flashing.md)).

**Why did the chip reset?** `Rp2350Watchdog::new` captures three pieces of evidence before it writes anything: `WATCHDOG.REASON` (bit 0 `TIMER`, bit 1 `FORCE`, both zero after a hardware reset), `POWMAN.CHIP_RESET` (which chip-level reset happened last; system-level resets do not update it), and `WATCHDOG.SCRATCH4`, where `start` leaves a marker ([`firmware/pico2/src/watchdog.rs:77-94`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/watchdog.rs#L77-L94)). The marker exists because the bootrom's own reboot routine (used by `picotool reboot`, by the drag-and-drop loader after a UF2 is written, and by the SDK's `watchdog_reboot`) also arms the watchdog timer, so `REASON.TIMER` alone cannot tell "this application stopped feeding" from "something rebooted the chip on purpose"; that routine always rewrites `SCRATCH4` ([`firmware/pico2/src/watchdog.rs:96-110`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/watchdog.rs#L96-L110)). The decision table is under [Algorithms and processing](#reset-reason-classification).

**Scratch registers.** `SCRATCH0` to `SCRATCH7` keep their contents through every reset short of a chip-level one, and every chip-level reset (power-on, brown-out, the RUN pin, a debugger reset) clears them ([`firmware/pico2/src/watchdog.rs:129-139`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/watchdog.rs#L129-L139); §7.3, [`docs/extracted/rp2350-datasheet.md:35998-35999`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/docs/extracted/rp2350-datasheet.md#L35998-L35999)). That makes them the place for a note to the next boot that unplugging the board erases. rustos gives the application only two of them. The bootrom reads `SCRATCH4` to `SCRATCH7` as its boot vector, and a one-shot reboot (such as the flash update after a UF2 download) overwrites `SCRATCH2` and `SCRATCH3`, which are otherwise free for user values (§5.2.4, [`docs/extracted/rp2350-datasheet.md:27533-27546`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/docs/extracted/rp2350-datasheet.md#L27533-L27546), [`docs/extracted/rp2350-datasheet.md:27590-27597`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/docs/extracted/rp2350-datasheet.md#L27590-L27597)), so the `Scratch` enum names only `SCRATCH0` and `SCRATCH1` ([`firmware/pico2/src/watchdog.rs:141-149`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/watchdog.rs#L141-L149)).

#### GPIO pins across a watchdog reset

The `RESETS` stage puts `IO_BANK0` and `PADS_BANK0` back into reset, but whether a pin follows depends on its pad's isolation latch ([`firmware/pico2/src/watchdog.rs:151-183`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/watchdog.rs#L151-L183); §9.7, [`docs/extracted/rp2350-datasheet.md:43463-43520`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/docs/extracted/rp2350-datasheet.md#L43463-L43520)):

- A pad whose `ISO` bit is 0 (transparent; the GPIO driver clears it when it configures a pin) returns to its reset state when the pad registers are reset: no function selected so the output is off, input disabled, pulled down (§9.3, [`docs/extracted/rp2350-datasheet.md:43032-43047`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/docs/extracted/rp2350-datasheet.md#L43032-L43047)).
- A pad whose `ISO` bit is 1 keeps the output enable, level and pulls it had when it was isolated, even a pin driven high. A `RESETS`-driven pad reset does not change the `ISO` bits; a power-down of the switched-core domain sets them all to 1.

So with the scope rustos uses, a configured output should drop to high impedance with a weak pull-down. The datasheet does not state the watchdog case outright, and **it has not been checked on hardware**. The rule that does not depend on which reading is right: configure safety-critical outputs, driven to their safe level, first thing after boot, and make the external circuit treat a high-impedance pin as off. The GPIO driver writes the output low and sets up the pad before it clears `ISO`, so the pin goes from its latched state straight to driven low ([`firmware/pico2/src/watchdog.rs:177-183`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/watchdog.rs#L177-L183)). On the keyer box the key pin also has a **required external 4.7 kΩ pull-down** to ground, because erratum RP2350-E9 can leave an undriven pad near 2 V, enough to key a radio; that resistor must never be removed ([`docs/keyer.md:59-64`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/docs/keyer.md#L59-L64); the canonical list of such rules is [13 Safety rules](https://github.com/robinonsay/cw-message-gateway/blob/claude/handover-docs-us00cn/docs/handover/13-safety-rules.md)).

On the keyer box the external circuit is an **inverting switch**: GP16 high lights the PC817 optocoupler's LED and closes the key, so pin low or undriven means key open ([`docs/keyer.md:57-58`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/docs/keyer.md#L57-L58)). Low is the safe level only because of that switch (a PC817 or one transistor), whose output is open whenever GP16 is low or undriven. **Never-loosen rule: a bare GPIO must never drive a radio that keys on a low line.** Every safe state of the box, including the pulled-down pad after a watchdog reset, is pin low, and on such a radio pin low would key it; the audit grades a Pico 2 pin wired straight to the key contact NO-GO ([`docs/keyer.md:966-976`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/docs/keyer.md#L966-L976); rule 2.4 on [13 Safety rules](https://github.com/robinonsay/cw-message-gateway/blob/claude/handover-docs-us00cn/docs/handover/13-safety-rules.md)).

### `common::reset`

All five are `pub unsafe fn`. `clr_reset_reg`, `set_reset_reg` and `cycle_reset` write the chip-wide `RESETS.RESET`, so the caller promises to touch only its own blocks; `wait_for_reset_done` and `is_reset_done` only read `RESET_DONE` ([`firmware/pico2/src/common/reset.rs:196-199`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/reset.rs#L196-L199), [`firmware/pico2/src/common/reset.rs:218-220`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/reset.rs#L218-L220)), and `wait_for_reset_done` can hang. The module has no shared bit constants; each driver defines its own mask (see [The reset controller](#the-reset-controller)).

## Algorithms and processing

### Clock bring-up (`Rp2350Clocks::new`)

`init` runs seven steps ([`firmware/pico2/src/clocks.rs:389-425`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/clocks.rs#L389-L425); the order and its reasons are documented at [`firmware/pico2/src/clocks.rs:51-71`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/clocks.rs#L51-L71)):

1. **Resus off.** `CLK_SYS_RESUS_CTRL` = 0, so the brief absence of `clk_sys` edges during a switch cannot trigger the hardware's "resuscitation" back to the ROSC ([`firmware/pico2/src/clocks.rs:393-394`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/clocks.rs#L393-L394)). Resus stays off afterwards; nothing re-enables it, so for the rest of the program nothing in hardware recovers a stopped `clk_sys`. The datasheet describes resus as a debugging aid that cannot help when `clk_ref` has also stopped (§8.1.4, [`docs/extracted/rp2350-datasheet.md:37970-37997`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/docs/extracted/rp2350-datasheet.md#L37970-L37997)).
2. **Crystal.** `start_xosc` writes `STARTUP.DELAY` = 282 first (the XOSC's own timer decides when `STATUS.STABLE` rises, so it must be programmed before enabling), then `CTRL` = `0xfab << 12 | 0xaa0`, then spins on `STATUS.STABLE` ([`firmware/pico2/src/clocks.rs:445-460`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/clocks.rs#L445-L460)). The delay is 12 000 cycles per ms × 6 ms ÷ 256 = 281.25, rounded up to 282: the datasheet's 1 ms for the reference crystal (§8.2.4, [`docs/extracted/rp2350-datasheet.md:40714-40731`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/docs/extracted/rp2350-datasheet.md#L40714-L40731)) times the SDK's default margin of 6 ([`firmware/pico2/src/clocks.rs:314-324`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/clocks.rs#L314-L324)). Writing the enable code again during a warm restart is harmless.
3. **Off the PLLs.** `clk_sys` to glitchless source 0 (`clk_ref`), then `clk_ref` to glitchless source 0 (ROSC), each waiting for `SELECTED`. Now neither clock depends on a PLL, so the PLLs can be reset even after a debugger warm reset left them in use ([`firmware/pico2/src/clocks.rs:399-403`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/clocks.rs#L399-L403)).
4. **PLLs.** `start_pll` for `PLL_SYS` then `PLL_USB` ([`firmware/pico2/src/clocks.rs:405-407`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/clocks.rs#L405-L407)).
5. **`clk_ref` = XOSC ÷ 1** through `switch_glitchless` with no aux change ([`firmware/pico2/src/clocks.rs:409-410`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/clocks.rs#L409-L410)).
6. **`clk_sys` = aux `PLL_SYS` ÷ 1** through `switch_glitchless` with `AUXSRC` = 0 ([`firmware/pico2/src/clocks.rs:412-419`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/clocks.rs#L412-L419)).
7. **`clk_usb` = `PLL_USB` ÷ 1, then `clk_peri` = `clk_sys` ÷ 1** through `switch_aux_only` ([`firmware/pico2/src/clocks.rs:421-423`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/clocks.rs#L421-L423)).

`start_pll(pll, reset_bit, cfg)` follows the datasheet's five-step sequence after a full reset of the PLL ([`firmware/pico2/src/clocks.rs:462-487`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/clocks.rs#L462-L487); §8.6.4, [`docs/extracted/rp2350-datasheet.md:42651-42661`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/docs/extracted/rp2350-datasheet.md#L42651-L42661)): `cycle_reset(bit)`; `CS` = `refdiv`; `FBDIV_INT` = `fbdiv`; clear `PWR.PD` and `PWR.VCOPD`; spin until `CS.LOCK`; `PRIM` = `postdiv1 << 16 | postdiv2 << 12`; clear `PWR.POSTDIVPD`. The post dividers are powered last so nothing downstream sees the VCO while it settles. The PLL is always reset first, whatever ran before, so the sequence starts from the power-down state.

`select_glitchless(clk, mask, src)`: write `SRC`, then spin until `SELECTED` bit `src` is set ([`firmware/pico2/src/clocks.rs:489-499`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/clocks.rs#L489-L499)).

`switch_glitchless(clk, mask, src, aux, div)` ([`firmware/pico2/src/clocks.rs:501-531`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/clocks.rs#L501-L531)):

```text
if div > DIV: DIV = div                 # a larger divisor goes in first
if aux = Some(shift, mask, value):
    select_glitchless(clk, 0)           # off the aux input (source 0 is never aux)
    CTRL.AUXSRC = value                 # now safe to change the glitchy mux
select_glitchless(clk, src)
DIV = div                               # a smaller divisor goes in last
```

`switch_aux_only(clk, auxsrc, div)` for generators without a glitchless mux ([`firmware/pico2/src/clocks.rs:533-553`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/clocks.rs#L533-L553)): clear `ENABLE`; spin until `ENABLED` reads 0 (the generator needs two cycles of its old source to stop, and polling `ENABLED` is the datasheet's advice when the destination may be much slower than `clk_sys`); write `AUXSRC`; write `DIV` (stopped, so no intermediate speed); set `ENABLE`; spin until `ENABLED` reads 1.

`start_clk_adc` is `switch_aux_only(clk_adc, PLL_USB, ÷1)`, run by `Rp2350Adc::new` after the pin blocks are released and before the ADC is reset; the ADC's registers time out on the bus while `clk_adc` is stopped ([`firmware/pico2/src/clocks.rs:427-443`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/clocks.rs#L427-L443), [`firmware/pico2/src/adc.rs:447-450`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/adc.rs#L447-L450)).

### Timer read and delays

`now()` ([`firmware/pico2/src/timer.rs:207-224`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/timer.rs#L207-L224)):

```text
hi = TIMERAWH
loop:
    lo = TIMERAWL
    hi2 = TIMERAWH
    if hi2 == hi: return hi << 32 | lo
    hi = hi2                          # the low word wrapped between the reads; retry
```

The latching pair `TIMELR`/`TIMEHR` is avoided on purpose: reading `TIMELR` latches `TIMEHR` for whoever reads next, so two readers would corrupt each other ([`firmware/pico2/src/timer.rs:199-206`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/timer.rs#L199-L206)). The retry runs at most once per 2^32 µs (about 71.6 minutes), when the low word wraps.

`delay_us(us)` reads `start = now()` and spins with `spin_loop()` while `elapsed_since(start) <= us`. It uses `<=` rather than `<` because the first tick may arrive almost immediately after `start` was read, so the wait is at least `us` ([`firmware/pico2/src/timer.rs:239-246`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/timer.rs#L239-L246)).

### SysTick arithmetic

`SYST_CVR` counts down from `0xff_ffff` to 0 and reloads, one count per `clk_sys` cycle. `cycles()` returns `0xff_ffff - CVR`, a count that goes up modulo 2^24. The elapsed cycles between two readings `a` then `b` is `b.wrapping_sub(a) & CYCLES_MASK`, correct as long as the readings are less than one wrap (2^24 / 150 MHz ≈ 111.8 ms) apart ([`firmware/pico2/src/systick.rs:26-39`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/systick.rs#L26-L39)). keyer-core's `ClockCheck` accumulates exactly that into a 64-bit total and divides by `CYCLES_PER_MS` ([`crates/keyer-core/src/control.rs:123-136`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/crates/keyer-core/src/control.rs#L123-L136)).

### Watchdog start, feed, forced reset

`start(timeout_us)` ([`firmware/pico2/src/watchdog.rs:534-548`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/watchdog.rs#L534-L548)):

1. `load = clamp(timeout_us, 1, 0xff_ffff)`.
2. `CTRL` = 0: stops the count while reconfiguring and clears the three pause bits.
3. `configure_reset_scope()` ([`firmware/pico2/src/watchdog.rs:614-634`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/watchdog.rs#L614-L634)): release `SYSCFG` from reset if something left it there (never assert it, since its other registers may be in use) and wait for `RESET_DONE`; `PSM.WDSEL` = `0x01ff_fff3`; `POWMAN.WDSEL` = `0x5afe_0000` (password with every option off); `SYSCFG.AUXCTRL` |= 1.
4. `start_tick(Watchdog)`: 12 `clk_ref` cycles per tick.
5. `SCRATCH4` = `0x7275_7374`.
6. `LOAD` = `load`.
7. `CTRL` = `ENABLE` only (pause bits stay clear).
8. Remember `load` for `feed`; return it.

`feed()` writes `LOAD` = `load` if `load` ≠ 0 ([`firmware/pico2/src/watchdog.rs:556-562`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/watchdog.rs#L556-L562)). Feed from the place that proves the application is healthy, the end of the main loop, not from a timer interrupt that keeps running when the loop hangs ([`firmware/pico2/src/watchdog.rs:553-555`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/watchdog.rs#L553-L555)).

`force_reset()` runs `configure_reset_scope()`, spins `POWMAN_SWITCH_DELAY_LOOPS` = 64 × (`CLK_SYS_HZ` / `CLK_REF_HZ`) = 768 iterations so the power manager can move off `clk_ref` (the datasheet gives no figure; the bootrom relies on about 5 `clk_ref` cycles), then sets `CTRL.TRIGGER` and spins until the reset lands ([`firmware/pico2/src/watchdog.rs:346-350`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/watchdog.rs#L346-L350), [`firmware/pico2/src/watchdog.rs:598-611`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/watchdog.rs#L598-L611)). `TRIGGER` does not need `ENABLE`.

### Reset-reason classification

`new` reads the snapshot, clears `SCRATCH4` if it holds the marker (so a later reset reports `WatchdogTimeout` only if `start` ran again), and classifies with a pure `const fn` ([`firmware/pico2/src/watchdog.rs:429-443`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/watchdog.rs#L429-L443), [`firmware/pico2/src/watchdog.rs:490-506`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/watchdog.rs#L490-L506)):

| `REASON.FORCE` | `REASON.TIMER` | `SCRATCH4` | Result |
|---|---|---|---|
| 1 | any | any | `WatchdogForced(ForcedBy::Trigger)` |
| 0 | 1 | `0x7275_7374` | `WatchdogTimeout` |
| 0 | 1 | anything else | `WatchdogForced(ForcedBy::Reboot)` |
| 0 | 0 | any | `ChipReset(chip_reset_cause(CHIP_RESET))` |

`chip_reset_cause` expects one flag; if several are set it takes the first in this order, the one that resets the most: `HAD_POR` → `PowerOn`, `HAD_BOR` → `Brownout`, `HAD_RUN_LOW` → `RunPin`, `HAD_DP_RESET_REQ` → `DebuggerReset`, `HAD_RESCUE` → `DebuggerRescue`, any `HAD_WATCHDOG_RESET_*` → `WatchdogChipLevel`, `HAD_SWCORE_PD` → `SwitchedCorePowerDown`, `HAD_GLITCH_DETECT` → `GlitchDetector`, `HAD_HZD_SYS_RESET_REQ` → `RiscvDebuggerReset`, none → `Unknown` ([`firmware/pico2/src/watchdog.rs:445-469`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/watchdog.rs#L445-L469)).

Limits of the evidence, all **unverified on hardware** ([`firmware/pico2/src/watchdog.rs:96-127`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/watchdog.rs#L96-L127)):

- The marker survives the bootrom only if the bootrom clears `SCRATCH4` solely for a valid boot-vector request, as §5.2.2 (Table 450) and an earlier sentence of §5.2.4 say ("If the numbers match, the Bootrom zeroes SCRATCH4", [`docs/extracted/rp2350-datasheet.md:27541-27542`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/docs/extracted/rp2350-datasheet.md#L27541-L27542)). A later sentence ([`docs/extracted/rp2350-datasheet.md:27544-27546`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/docs/extracted/rp2350-datasheet.md#L27544-L27546)) speaks of "the bootrom clearing SCRATCH4 each boot"; if that were literally true, every timeout would be reported as `WatchdogForced(Reboot)`.
- A debugger warm reset (`SYSRESETREQ`) clears `REASON`, so it is reported as `ChipReset` with whatever chip-level cause came before it.
- The datasheet does not say which `REASON` bit the bootrom's reboot leaves; the bootrom source arms the timer, hence `TIMER`.

## Programming against it

All examples are `no_std` application code in a crate set up as [02 Boot and runtime](02-boot-runtime.md) describes; they are sketches against the signatures above, not code from the repository, except where a permalink says otherwise.

### Bring up the clocks and time, and blink without a calibrated loop

```rust
#![no_std]
#![no_main]

use api::common::Write;
use api::gpio::Gpio;
use pico2::clocks::Rp2350Clocks;
use pico2::common::board::Rp2350;
use pico2::gpio::gpio::Rp2350Gpio;
use pico2::timer::Rp2350Timer;

pico2::entry!(main);

#[panic_handler]
fn panic(_: &core::panic::PanicInfo) -> ! { loop {} }

fn main() -> ! {
    let board = Rp2350::take().unwrap();
    let mut gpio = Rp2350Gpio::new(board.gpio);
    let mut led = gpio.output_from_handle(board.pins.led).unwrap();
    let clocks = Rp2350Clocks::new(board.clocks);          // after the LED pin: everything below runs at 150 MHz
    let timer = Rp2350Timer::new(board.timer, &clocks);    // 1 µs tick, never paused by a debugger
    loop {
        let _ = led.write(true);
        timer.delay_ms(250);
        let _ = led.write(false);
        timer.delay_ms(250);
    }
}
```

The template application (`templates/pico2/src/main.rs`) still blinks with a counted loop "calibrated by eye" and says there is no configured timer yet ([`templates/pico2/src/main.rs:54-60`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/templates/pico2/src/main.rs#L54-L60)); the timer above is the replacement.

### Deadlines without blocking

```rust
let started = timer.now();
// ... each pass of the loop:
if timer.elapsed_since(started) >= 1_000_000 {
    // one second has passed: act, then restart the deadline
}
```

Keep all deadlines on `now()` in microseconds (or `now() / 1000` in milliseconds, as the keyer does). Do not call `delay_*` in a loop that must also feed the watchdog or poll USB.

### Check that time is still running

```rust
use pico2::systick::{Rp2350SysTick, CYCLES_MASK, CYCLES_PER_MS};

let systick = Rp2350SysTick::new(board.systick, &clocks);   // on the core that will read it
let (mut t0, mut c0) = (timer.now(), systick.cycles());
// ... at least every 100 ms (less than one 112 ms SysTick wrap):
let (t1, c1) = (timer.now(), systick.cycles());
let cpu_ms = u64::from(c1.wrapping_sub(c0) & CYCLES_MASK) / u64::from(CYCLES_PER_MS);
let clock_ms = (t1 - t0) / 1000;
// a stopped microsecond tick shows as clock_ms far below cpu_ms
(t0, c0) = (t1, c1);
```

This is the idea behind keyer-core's `ClockCheck`, which uses a 50 ms window and the never-loosen thresholds above ([`crates/keyer-core/src/control.rs:86-136`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/crates/keyer-core/src/control.rs#L86-L136)). Reuse that code rather than writing a second copy.

### Watchdog with state kept across a reset

```rust
use pico2::watchdog::{ResetReason, Rp2350Watchdog, Scratch};

let mut watchdog = Rp2350Watchdog::new(board.watchdog, &clocks);  // early: reads the evidence
let restarted = watchdog.reset_reason() == ResetReason::WatchdogTimeout;
let saved = watchdog.scratch(Scratch::Scratch0);   // 0 after a power-up
// ... bring up USB and anything else that blocks, then:
let used = watchdog.start(100_000);                // 100 ms; returns the clamped value
loop {
    // ... one pass of work ...
    watchdog.set_scratch(Scratch::Scratch0, state_word);
    watchdog.feed();                                // last thing in the pass
}
```

Validate what you read back: the scratch registers may hold another firmware's data. The keyer stores a 16-bit magic number and a check byte with its state and treats anything that does not decode as nothing saved ([`crates/keyer-core/src/keyer.rs:241-288`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/crates/keyer-core/src/keyer.rs#L241-L288)).

To restart deliberately, call `watchdog.force_reset()`; the next boot sees `WatchdogForced(ForcedBy::Trigger)`.

### Reset a block in a new driver

```rust
// Inside the pico2 crate this is `use crate::common::reset::...`.
use pico2::common::reset::{clr_reset_reg, cycle_reset, wait_for_reset_done};

// IO_BANK0 (bit 6) and PADS_BANK0 (bit 9), Table 534. reset.rs exports no bit
// constants: each driver defines its own, as pwm.rs:319 and adc.rs:289 do.
const RESET_IO_PADS: u32 = (1 << 6) | (1 << 9);
const RESET_MYBLOCK: u32 = 1 << N;           // your block's bit from Table 534, with the citation

unsafe {
    clr_reset_reg(!RESET_IO_PADS);           // shared pin blocks: release only (note the !)
    wait_for_reset_done(RESET_IO_PADS);
    cycle_reset(RESET_MYBLOCK);              // own block: assert, release, wait (no !)
}
```

This is the PWM driver's own sequence ([`firmware/pico2/src/pwm.rs:614-620`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L614-L620)). Never put bit 7 or 10 in a mask given to `set_reset_reg` or `cycle_reset`. The full driver pattern is on [07 Writing a driver](07-writing-a-driver.md).

### Use an atomic alias

The PWM driver's real code, inside the `pico2` crate (`Pwm` is that driver's private `#[repr(C)]` layout of the block; [`firmware/pico2/src/pwm.rs:206`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L206), [`firmware/pico2/src/pwm.rs:277-285`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L277-L285), [`firmware/pico2/src/pwm.rs:794-801`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L794-L801)):

```rust
use crate::common::reg::RegAddr;

/// The atomic set alias (+0x2000): a write sets exactly the bits written.
const fn pwm_set() -> *mut Pwm {
    (RegAddr::PWM as usize + 0x2000) as *mut Pwm
}

/// The atomic clear alias (+0x3000): a write clears exactly the bits written.
const fn pwm_clr() -> *mut Pwm {
    (RegAddr::PWM as usize + 0x3000) as *mut Pwm
}

// One channel's half of a slice's CC register, never touching the other half:
unsafe {
    if value {
        (&raw mut (*pwm_set()).slice[slice].cc).write_volatile(level << shift);
    } else {
        (&raw mut (*pwm_clr()).slice[slice].cc).write_volatile(CC_HALF_MASK << shift);
    }
}
```

Not for SIO, the USB dual-port RAM or SysTick, which have no aliases.

## Changing it

**Rules first.** These drivers carry safety behaviour the keyer box depends on. Never re-enable the watchdog's or `TIMER0`'s debugger-pause bits, never narrow the watchdog's reset scope (it must restart both cores and put every block back in reset), never move the application's scratch words out of `SCRATCH0`/`SCRATCH1` into `SCRATCH2` to `SCRATCH7` (the bootrom uses those, [`firmware/pico2/src/watchdog.rs:141-149`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/watchdog.rs#L141-L149)), never move the marker out of `SCRATCH4` (the classification depends on the bootrom's reboot routine rewriting that register, [`firmware/pico2/src/watchdog.rs:96-103`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/watchdog.rs#L96-L103), [`firmware/pico2/src/watchdog.rs:223-226`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/watchdog.rs#L223-L226)), and never change a box limit or the clock-check thresholds in keyer-core (never-loosen rules, [13 Safety rules](https://github.com/robinonsay/cw-message-gateway/blob/claude/handover-docs-us00cn/docs/handover/13-safety-rules.md)). Any rustos change that reaches the keyer image means a new rustos pin in `firmware/pico2-keyer/Cargo.toml`, a new UF2, and a fresh pass through the safety audit with a new hash before anything is flashed ([14 Audit, bench and flashing](https://github.com/robinonsay/cw-message-gateway/blob/claude/handover-docs-us00cn/docs/handover/14-audit-bench-flashing.md)). Even a pin move with no source change can change the UF2 ([`firmware/pico2-keyer/Cargo.toml:21-29`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/Cargo.toml#L21-L29)).

**How to check a change.** rustos has no CI and `firmware/pico2` has no tests. Build it with `cargo pico2` and `cargo pico2 --release` ([`.cargo/config.toml:6-7`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/.cargo/config.toml#L6-L7)); the `const` asserts in these files are the tests, and they fail the build. If you touch `board.rs` or `define_board!`, also run `cargo test` at the rustos root, which runs the `api` crate's host tests. Then build the keyer firmware against the change (point its `api` and `pico2` dependencies at your branch or a local checkout, as [08 Changes for cw-message-gateway](08-changes-for-cw-gateway.md) shows under "Build against a rustos branch or a local checkout") and let cw-message-gateway's CI run: its keyer job checks from the machine code that the fault handlers open the key first ([`.github/workflows/ci.yml:185-186`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/.github/workflows/ci.yml#L185-L186)), and `cargo test --all` runs keyer-core's host tests ([`.github/workflows/ci.yml:33`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/.github/workflows/ci.yml#L33)). Behaviour on hardware is checked only on the bench, on Robin's (the project owner's) go.

## Known bugs, limits and flakes

- **Uncited claim in `reset.rs`.** "Reads and writes to a held peripheral ... do nothing useful" and "accepted by the bus and discarded" cite nothing, and the datasheet's reset chapter does not say it ([`firmware/pico2/src/common/reset.rs:13-17`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/reset.rs#L13-L17), [`firmware/pico2/src/common/reset.rs:153-155`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/reset.rs#L153-L155)). Flagged by the safety audit. The PWM fault path does not rely on it ([`firmware/pico2/src/pwm.rs:709-713`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/pwm.rs#L709-L713)).
- **No time limits on hardware waits.** `wait_for_reset_done`, the XOSC `STABLE` wait, both PLL `LOCK` waits, the `SELECTED` and `ENABLED` polls all spin for ever if the hardware never answers ([`firmware/pico2/src/common/reset.rs:200-208`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/reset.rs#L200-L208), [`firmware/pico2/src/clocks.rs:458`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/clocks.rs#L458), [`firmware/pico2/src/clocks.rs:483`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/clocks.rs#L483), [`firmware/pico2/src/clocks.rs:497`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/clocks.rs#L497), [`firmware/pico2/src/clocks.rs:545`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/clocks.rs#L545)). On the keyer the key and PTT are already driven low before `Rp2350Clocks::new`; a hang there before `start` is not ended by the watchdog.
- **The watchdog shares the reference clock.** If the XOSC or `clk_ref` stops, `TIMER0` and the watchdog both stop counting; nothing on the chip then resets it, and only software comparing against SysTick can notice ([The watchdog counts the same kind of tick](#time-the-tick-timer0-and-systick)). This is the safety audit's KB-5 (`audit/report.md`, project files); see gateway [08 Keyer box: firmware](https://github.com/robinonsay/cw-message-gateway/blob/claude/handover-docs-us00cn/docs/handover/08-keyer-box-firmware.md) and rule 1.13 on [13 Safety rules](https://github.com/robinonsay/cw-message-gateway/blob/claude/handover-docs-us00cn/docs/handover/13-safety-rules.md).
- **Non-atomic reset helpers.** `clr_reset_reg` and `set_reset_reg` read, modify and write `RESETS.RESET`; the code itself notes that the `+0x3000` clear alias would avoid the window ([`firmware/pico2/src/common/reset.rs:116-123`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/reset.rs#L116-L123)). Safe today because only core 0 calls them, during bring-up; in PR #31, core 1's memory protection unit faults any access to `RESETS` ([`firmware/pico2-keyer/src/core1.rs:16-22`](https://github.com/robinonsay/cw-message-gateway/blob/bc5062ae4f56ae1f9949b3b067218c7e675d88f8/firmware/pico2-keyer/src/core1.rs#L16-L22)).
- **SysTick is per core but the type does not say so.** `Rp2350SysTick` is a zero-sized type, so Rust makes it `Send` and `Sync`; nothing stops core 1 from calling `cycles()`, which would read core 1's own, never-started SysTick ([`firmware/pico2/src/systick.rs:41-43`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/systick.rs#L41-L43), [`firmware/pico2/src/systick.rs:89-93`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/systick.rs#L89-L93)). No code does this today.
- **`start(0)` resets almost at once** (clamped to 1 µs), and **`feed()` before `start()` does nothing** without telling the caller ([`firmware/pico2/src/watchdog.rs:535`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/watchdog.rs#L535), [`firmware/pico2/src/watchdog.rs:557-559`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/watchdog.rs#L557-L559)).
- **`delay_us`/`delay_ms` do not feed the watchdog** ([`firmware/pico2/src/timer.rs:236-238`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/timer.rs#L236-L238)); a delay longer than the timeout resets the chip.
- **`delay_us(u64::MAX)` never returns**: the loop's `<=` test is always true for that value ([`firmware/pico2/src/timer.rs:243`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/timer.rs#L243)). `delay_ms` cannot reach it (its largest argument gives about 4.3 × 10^12 µs).
- **The forced-reset wait is approximate.** `64 * (CLK_SYS_HZ / CLK_REF_HZ)` uses integer division (150/12 truncates to 12), so the loop runs 768 iterations; at one iteration per cycle or more that is at least about 61 `clk_ref` cycles, against the bootrom's 5. Not a bug in practice; unverified on hardware ([`firmware/pico2/src/watchdog.rs:346-350`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/watchdog.rs#L346-L350)).
- **Unverified on hardware** (all stated in the code): one watchdog count per tick ([`firmware/pico2/src/timer.rs:31-40`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/timer.rs#L31-L40)); leaving the power manager on the low-power oscillator for the life of the program ([`firmware/pico2/src/watchdog.rs:61-63`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/watchdog.rs#L61-L63)); the marker surviving the bootrom and the bootrom's reboot leaving `REASON.TIMER` ([`firmware/pico2/src/watchdog.rs:96-127`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/watchdog.rs#L96-L127)); the pad states after a watchdog reset ([`firmware/pico2/src/watchdog.rs:172-177`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/watchdog.rs#L172-L177)).
- **Open question, not addressed by the code or the sections it cites:** §12.9.1 lists chip-level resets as what resets the watchdog ([`docs/extracted/rp2350-datasheet.md:89710-89715`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/docs/extracted/rp2350-datasheet.md#L89710-L89715)), and the watchdog is neither a PSM stage ([`firmware/pico2/src/watchdog.rs:269-273`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/watchdog.rs#L269-L273)) nor a `RESETS` block ([`firmware/pico2/src/common/reset.rs:21-32`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/reset.rs#L21-L32)), so a PSM-level watchdog reset presumably leaves it alone (inferred). `new` does not stop the watchdog. Whether `CTRL.ENABLE` is still set when the program starts again after a watchdog reset is not stated; if it were, the time between boot and `start` (USB alone blocks about 10 ms) would matter. Check this on the bench.
- **No hardware alarms or interrupts.** `Rp2350Timer` only reads the counter; `TIMER1`, the alarms, `PAUSE` and `LOCKED` are unused, and any code that wrote `TIMER0.PAUSE` = 1 would stop time (the SysTick check is what would notice).
- **Seven private `unsafe fn`s in `clocks.rs` and `watchdog.rs` have no `# Safety` section** (`init`, `start_xosc`, `start_pll`, `select_glitchless`, `switch_glitchless`, `switch_aux_only`, `configure_reset_scope`), unlike every public one; see [07 Writing a driver](07-writing-a-driver.md).
- **`MAX_GPIO_PIN`'s compile-time check rejects nothing**: the GPIO pin types' `_VALID` assertion is never evaluated; only the board's pin list keeps pins in range ([`firmware/pico2/src/common/mod.rs:29-35`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/mod.rs#L29-L35)).
- **Stale doc comments in these files** (none changes behaviour; [09 Work left and known issues](09-work-left-known-issues.md), W5): `reset.rs` says the module has "three functions" (it has five, [`firmware/pico2/src/common/reset.rs:3-5`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/common/reset.rs#L3-L5)); `Rp2350Clocks::new` says "call this first, before any other driver" and that no GPIO is configured yet, which the keyer and the watchdog's own example contradict ([`firmware/pico2/src/clocks.rs:378-382`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/clocks.rs#L378-L382); follow [Bring-up order](#bring-up-order)); `Rp2350Clocks`'s doc names only the timer, watchdog and USB as users of `&Rp2350Clocks`, leaving out SysTick, PWM and the ADC ([`firmware/pico2/src/clocks.rs:367-369`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/clocks.rs#L367-L369)); the blinky template says there is no configured timer ([`templates/pico2/src/main.rs:54-55`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/templates/pico2/src/main.rs#L54-L55)).
- **Never run anywhere.** No firmware in either repository (gateway `main`, PR #30, PR #31) and no test calls `Rp2350Watchdog::reset_snapshot`, `time_remaining_us`, `is_running` or `force_reset`. `Rp2350Timer::delay_us` runs only through `Rp2350Usb::new`'s `delay_ms(10)` ([`firmware/pico2/src/usb/mod.rs:403`](https://github.com/robinonsay/rustos/blob/80bf5998a60a41b3741041062ff7e9c59caf95b2/firmware/pico2/src/usb/mod.rs#L403)), and `elapsed_since` only inside `delay_us` and PR #6's launch ([`firmware/pico2/src/multicore.rs:391`](https://github.com/robinonsay/rustos/blob/410dffa091e247e6e7546c7f2ff465f0af499d5a/firmware/pico2/src/multicore.rs#L391)). `pico2` has no tests, so these paths have never executed.

No flakes are known; none of these drivers has an automated test.

### What has run on a chip

One rustos image in this project's records has run on a real Pico 2: the keyer box file `eef8c126` (rustos `c9852112` sources), flashed on 2026-10-09 on a bare Pico 2 with nothing wired to a radio. It enumerated over USB and `hfnode keyer check` reported "all ok; nothing was keyed", "up 151 s, last started by POWER" (`bench/quansheng.md`, project files, log 2026-10-09 16:17Z and 16:19Z). The keyer's start-up order ([`firmware/pico2-keyer/src/main.rs:174-216`](https://github.com/robinonsay/cw-message-gateway/blob/44185fa9a00369c379d9d8af40ca307e3867e860/firmware/pico2-keyer/src/main.rs#L174-L216)) shows which of this page's drivers that exercised. The same table for every driver is on [09 Work left and known issues](09-work-left-known-issues.md), W4.
